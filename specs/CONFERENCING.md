## 1. Гибридный движок WebRTC

Платформа использует **гибридный движок**: выбор между P2P (Mesh) и SFU (Selective Forwarding Unit) определяется количеством участников и состоянием сетевого канала.

### 1.1. Логика выбора (MVP)

| Условие | Режим | Обоснование |
|:---|:---|:---|
| 1-to-1 (2 участника) | **P2P (Mesh)** | Минимальная задержка, без промежуточного сервера. |
| >2 участников | **SFU** | Сервер маршрутизирует потоки, экономя ресурсы клиентов. |
| P2P не установился за 5 секунд (ICE-кандидаты не согласованы) | **SFU + TURN** | Fallback при строгих NAT/firewall. |

**Триггер переключения** — количество участников в комнате (определяется на стороне сервера при создании/подключении к комнате). Логика:

1. При создании комнаты сервер (крейт `api`) фиксирует ожидаемое количество участников.
2. Клиент при подключении получает конфигурацию: `p2p` (если 2 участника) или `sfu` (если >2).
3. Если P2P-соединение не устанавливается за 5 секунд (ICE-кандидаты не согласованы), клиент автоматически переключается на SFU + TURN.

### 1.2. Инструменты

* Интерактивная доска (Whiteboard).
* Шеринг экрана.
* Совместный просмотр видео.
* Поднятие руки.
* Опросы в реальном времени.

Все инструменты работают как в P2P, так и в SFU-режиме. Различия — только в транспорте медиапотока.

### 1.3. Ограничения MVP

В MVP **не поддерживается** динамическое переключение P2P → SFU **внутри активной сессии**:

* Если сессия началась в P2P и качество канала деградировало — клиент **не переключается** на SFU на лету.
* Требуется **перезаход в комнату** (выйти и зайти снова), чтобы клиент получил новую конфигурацию.
* Причины ограничения: сложность управления состоянием медиапотока при переключении (потеря потока, необходимость renegotiation с обеих сторон), отсутствие стандартизированного WebRTC-механизма для seamless-переключения.

Это ограничение **снимается** в версии 1.x (см. [`ROADMAP.md`](ROADMAP.md) §«Планируемые направления» — пункт про ВКС). Точные сроки — TBD.

## 2. P2P (Mesh) для 1-to-1

* **Применение:** комнаты с 2 участниками.
* **Архитектура:** прямое WebRTC-соединение между двумя клиентами; медиапоток идёт напрямую, без промежуточного сервера.
* **Преимущества:** минимальная задержка, минимальная нагрузка на инфраструктуру.
* **Ограничения:**
  * Требует успешного ICE-согласования (STUN для определения внешнего адреса).
  * При строгих NAT/firewall — может потребоваться TURN (fallback на SFU + TURN).
* **Fallback:** если P2P не установился за 5 секунд — автоматическое переключение на SFU + TURN.

## 3. SFU (Selective Forwarding Unit) для групп

* **Применение:** комнаты с 3+ участниками; также fallback для P2P.
* **Архитектура:** сервер (SFU) принимает медиапотоки от каждого участника и маршрутизирует их остальным. Клиент отправляет **один** поток на сервер, а не N-1 потоков напрямую, как в Mesh.
* **Кандидаты SFU:** Mediasoup, Janus.
* **Преимущества:** экономия ресурсов клиентов (особенно аплинка), масштабируемость до десятков участников в комнате.
* **Ограничения:**
  * Сервер SFU — дополнительная точка отказа; требует мониторинга и масштабирования.
  * Для больших комнат (50+ участников) — требуется Simulcast / SVC для оптимизации.

## 4. Закрытый контур (Air-gapped)

Для Air-gapped On-Premise разворачиваются **локальные TURN/STUN** серверы, работающие внутри LAN. Внешние STUN/TURN не используются.

**Критично:** в Air-gapped **SFU и TURN/STUN разворачиваются по умолчанию** (не опционально). Причина:

* Без SFU fallback при неудачном P2P невозможен — комната с 2 участниками на строгом firewall не установит соединение.
* Без TURN не работает ICE-согласование в сетях с симметричным NAT.

Инфраструктурные детали (образы, порты, конфигурация) — в [`DEPLOY.md`](DEPLOY.md) §3.

## 5. Интеграция с Feature Flags и лицензированием

Доступность ВКС контролируется двумя механизмами:

* **`license.features.vks`** — коммерческое право тенанта на использование ВКС (см. [`LICENSING.md`](LICENSING.md) §2.2).
* **`feature_flags.vks`** — операционное состояние (например, beta-тест ВКС для ограниченного числа тенантов, см. [`FEATURE_FLAGS.md`](FEATURE_FLAGS.md) §1.1).

Каскадная проверка: `license.features.vks` → `feature_flags.vks` → бизнес-логика. При отсутствии права — `403 feature_not_licensed`; при выключенном флаге — `403 feature_not_enabled`.

## 6. Метрики и качество

Для ВКС собираются следующие метрики (через OpenTelemetry, см. [`DIAGNOSTICS.md`](DIAGNOSTICS.md) §4):

* **Latency** (задержка аудио/видео, p50/p95).
* **Packet loss** (потеря пакетов).
* **Jitter** (джиттер).
* **ICE-согласование:** время до установления соединения, использован ли TURN.
* **Режим соединения:** P2P / SFU.
* **Количество участников** в комнате.
* **Длительность сессии.**

Эти метрики используются для:

* мониторинга качества ВКС (алерты при деградации);
* обоснования перехода на версию 1.x с динамическим переключением P2P → SFU;
* диагностики проблем в Air-gapped.

## 7. Ограничения и что НЕ входит в MVP

* **Динамическое переключение P2P → SFU внутри активной сессии** — не поддерживается (см. §1.3).
* **Запись вебинаров** — в плане (см. [`ROADMAP.md`](ROADMAP.md) §«Вебинары с записью»).
* **Транскрипция и live-субтитры** — не входит в MVP.
* **Simulcast / SVC для больших комнат** — опционально, зависит от выбранного SFU (Mediasoup поддерживает; Janus — ограниченно).
* **Виртуальные фоны / шумоподавление** — на стороне браузера (не в зоне ответственности платформы).
* **Кастомные раскладки** — базовые раскладки (сетка, спикер) в MVP; расширенные (pin, focus) — в 1.x.

## 8. Связь с ADR

Полноценный ADR по ВКС пока не создан. Возможные темы для ADR:

* Запись вебинаров и её интеграция с DAM.
