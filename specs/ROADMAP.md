# Roadmap (планы развития)

> Текущий этап — проектирование и разработка документации. Ниже — функциональные направления, вынесенные в план. Матрица текущего статуса — в [`STATUS.md`](STATUS.md). Уже специфицированные модули, находящиеся в реализации, в этом файле не дублируются и помечаются ссылкой на соответствующий источник истины.

## Аналитика обучения (Learning Analytics)

Сбор данных уже покрыт LRS (xAPI → TimescaleDB/ClickHouse, см. [`DB_SCHEMA.md`](DB_SCHEMA.md) §2 и [`STATUS.md`](STATUS.md) строка «Движок LRS»). Инструментирование трейсов и метрик — на базе OpenTelemetry (см. [`DIAGNOSTICS.md`](DIAGNOSTICS.md) §4 и [`NFR.md`](NFR.md) §7).

В план выносится слой **осмысления**:

* дашборды прогресса, вовлечённости, completion rates;
* когортные отчёты;
* алерты по «застреванию» студентов;
* интеграция с внешними BI (Metabase, Superset, Grafana) через OTLP + LRS-экспорт.

## Сертификация и валидация

Базовые триггеры выпуска и публичная верификация сертификатов уже специфицированы — см. [`SPECIFICATION.md`](SPECIFICATION.md) §4 «Сертификация и верификация». В план выносится:

* поддержка внешних форматов верификации (Open Badges / Blockcerts);
* экспорт сертификатов во внешние системы подтверждения квалификаций;
* расширенный публичный реестр (публичный API верификации по `verification_hash`).

## Платежи и биллинг

Подписки, разовые платежи, выставление счетов, интеграция с платёжными провайдерами, учёт налогов на уровне тенанта (см. [`DB_SCHEMA.md`](DB_SCHEMA.md) §1.2, таблица `tenants`).

## Поиск и рекомендации

Полнотекстовый поиск по контенту — кандидаты Elasticsearch / Meilisearch. Рекомендации курсов и материалов на основе истории и профиля пользователя.

> Выбор поискового движка (и его включение в [`DEPLOY.md`](DEPLOY.md) §1 и §3) будет сделан на более поздних этапах, аналогично выбору LRS (TimescaleDB vs ClickHouse) и очереди задач (Tokio vs River/Redis).

## Вебинары с записью

Запись вебинаров, хранение в DAM, публикация в курсе. Проводятся поверх встроенной ВКС, которая уже специфицирована в [`CONFERENCING.md`](CONFERENCING.md) и внесена в [`STATUS.md`](STATUS.md) как требование в реализации (P2P, SFU, whiteboard, локальные TURN/STUN). В план выносится именно **запись и публикация**, а не сама ВКС.

## Мобильное приложение

Нативные мобильные клиенты (технологии будут определены позже). Ключевые сценарии: офлайн-доступ к контенту, push, прохождение заданий, коммуникации.

> Для iOS-сегмента нативное приложение — **приоритетное направление**: PWA на iOS не закрывает сценарий полного офлайна из-за лимитов IndexedDB и отсутствия Background Sync (см. [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §1.3).

## Аудит и соответствие (Compliance)

Журнал аудита административных действий, экспорт данных субъекта, право на забвение, согласия — см. [`STANDARDS.md`](STANDARDS.md) §«Безопасность и приватность». Retention-политики уже специфицированы — см. [`STANDARDS.md`](STANDARDS.md) §«Политики удержания данных» и [`DB_SCHEMA.md`](DB_SCHEMA.md) §1.2 (таблица `retention_policies`).

В план выносится:

* **SIEM-интеграции** — экспорт журналов аудита и OTel-трейсов во внешние SIEM (Splunk, Elastic Security, Wazuh);
* расширенный экспорт журналов аудита по требованию тенанта;
* автоматизированный GDPR-экспорт данных субъекта (эндпоинт + ZIP с полной выгрузкой);
* публичный регламент реагирования на инциденты.

## Планируемые направления (осознанно вне скоупа MVP)

Разделы ниже либо уже частично специфицированы, но требуют отдельного ADR и/или регламента перед реализацией, либо осознанно вынесены за MVP для Enterprise-сегмента.

### SCORM 2004 Sequencing & Navigation

Полноценная поддержка правил последовательности SCORM 2004 (sequencing rules, rollup, delivery controls). **Не входит** в базовый скоуп (см. [`STANDARDS.md`](STANDARDS.md) §SCORM «Ограничения»). Реализуется как отдельное расширение для Enterprise-тенантов, чьи курсы строго зависят от сложных правил навигации. Требует ADR: объём поддержки, интеграция с нативным `course_tree`, влияние на Calculations Engine.

### Application-Level Encryption (ALE)

Спецификация ALE зафиксирована в [`STANDARDS.md`](STANDARDS.md) §«Application-Level Encryption». Требует отдельного ADR перед реализацией:

* выбор KMS/Vault-схемы (HashiCorp Vault vs облачный KMS);
* формат детерминированного шифрования `email` (AES-SIV vs blind index);
* процедура включения ALE для существующего тенанта (миграция данных);
* регламент ротации ключей (DEK / KEK).

### Data Residency — процедура миграции тенанта между регионами

В [`STANDARDS.md`](STANDARDS.md) §«Data Residency и суверенитет данных» зафиксировано, что миграция тенанта между регионами — **не автоматическая** процедура с аудитом. Сам регламент миграции отсутствует. Требуется:

* ADR с процедурой (экспорт → перенос → импорт → валидация);
* инструменты для миграции Core-БД, LRS, DAM, KMS-ключей;
* процедура верификации целостности после переноса.

### OpenTelemetry — выбор backend

Инструментирование OTel зафиксировано в [`DIAGNOSTICS.md`](DIAGNOSTICS.md) §4, инфраструктура — в [`DEPLOY.md`](DEPLOY.md) §3. Backend для трейсов (Grafana Tempo / Jaeger / OpenSearch / Datadog) выбирается на этапе развертывания; в SaaS — по умолчанию один, в On-Premise — по требованию тенанта. Требует ADR при выборе конкретного backend для SaaS-поставки.

### Kill switch плагинов Контура Б (подпись и Revocation List)

Спецификация подписи, верификации и отзыва зафиксирована в [`PLUGIN.md`](PLUGIN.md) §7. Требует ADR перед реализацией:

* финальный формат `.wasm.sig` (подпись + метаданные);
* стратегия ротации release-ключа (двойной комплект на переходный период);
* формат Revocation List и частота его обновления;
* политика fail-open vs fail-closed при отсутствии сети (в [`PLUGIN.md`](PLUGIN.md) §7.3 зафиксирована fail-open по умолчанию; режим «strict revocation» — опция тенанта).

### Deprecation версий API — операционный регламент

Политика версионирования и deprecation зафиксирована в [`OPEN_API.md`](OPEN_API.md) §5 (RFC 8594, график T+0 / T+6 / T+12). Требует операционного регламента:

* кто инициирует deprecation (product owner / архитектурный комитет);
* инструмент для отправки `api.deprecation.announced` вебхука;
* шаблон migration guide;
* процедура проверки отсутствия активных вызовов перед sunset (по метрикам OTel).

### GraphQL — полноценная спецификация схемы

GraphQL упомянут как протокол в [`OPEN_API.md`](OPEN_API.md) §1, но полноценная спецификация отсутствует:

* схема запросов и мутаций;
* пагинация (Relay Cursor Connections);
* директива `@deprecated` и её взаимодействие с общей политикой версионирования;
* кэширование и persisted queries;
* авторизация на уровне полей (field-level auth).

Вынесено за MVP: REST-контракты покрывают все ключевые сценарии. GraphQL — оптимизация для фронтенда Leptos, добавляется по мере усложнения UI.
