# Тема: Выбор паттерна Shared Schema с PostgreSQL RLS для Strict Multi-tenancy

## Контекст и Постановка проблемы
Для реализации Enterprise-grade LMS-платформы требуется жесткая изоляция данных (Strict Multi-tenancy) между независимыми организациями (тенантами). Платформа должна поддерживать динамическое создание новых тенантов через API (динамический provisioning) без простоя системы и ручного вмешательства администратора. 

Рассматривались два основных архитектурных паттерна на уровне СУБД PostgreSQL:
1. **Isolated Schemas:** Создание отдельной физической схемы (`CREATE SCHEMA tenant_x`) со своим набором таблиц под каждую новую организацию.
2. **Shared Schema with Row-Level Security (RLS):** Использование единого набора таблиц, где каждая строка содержит сквозной ключ `tenant_id`, а разграничение доступа контролируется на уровне ядра СУБД через встроенные политики безопасности.

## Рассмотренные варианты и Трейд-оффы (Trade-offs)

### Вариант 1: Isolated Schemas (Изолированные схемы)
*   *Плюсы:* Максимальная ментальная изоляция на уровне таблиц. Проще делать резервное копирование и очистку данных отдельного клиента.
*   *Минусы:* Экстремальное усложнение миграций СУБД (при обновлении платформы нужно накатывать миграции на тысячи схем параллельно). Резкая деградация пула соединений (Connection Pool) бэкенда на Rust — Axum/Actix-web вынужден либо держать отдельные пулы к каждой схеме, либо динамически переключать `search_path`, что сводит на нет оптимизацию подготовленных запросов (Prepared Statements) в `SQLx`.

### Вариант 2: Shared Schema с Row-Level Security (RLS)
*   *Плюсы:* Идеально ложится на концепцию асинхронного бэкенда на Rust. Один пул соединений, высокая скорость выполнения подготовленных запросов. Динамический provisioning тенанта происходит мгновенно за одну стандартную транзакцию (`INSERT INTO tenants ...`). Единый и предсказуемый процесс миграции СУБД.
*   *Минусы:* Риск логической ошибки в коде бэкенда, которая может привести к утечке данных, если забыть прокинуть `WHERE tenant_id = ...`.

## Принятое решение
Утвержден **Вариант 2: Shared Schema с Row-Level Security (RLS)**. 

Для нивелирования рисков логических ошибок бэкенда изоляция переносится с уровня прикладных SQL-запросов на уровень ядра самой СУБД PostgreSQL:
1. Для всех таблиц тенантов принудительно включается RLS: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`.
2. Создается единая сквозная политика, которая аппаратно отсекает строки, не соответствующие локальному сессионному параметру `app.current_tenant_id`.
3. Бэкенд на Rust инкапсулирует логику авторизации в крейте `lms-database-db`. При каждом входящем запросе, прошедшем SSO, интерцептор транзакций выполняет императивную команду `SET LOCAL app.current_tenant_id = <id>` внутри пула. Прикладной код в репозиториях физически лишен возможности прочитать или изменить данные чужого тенанта.

## Последствия и Риски
*   **Производительность:** Накладные расходы PostgreSQL на валидацию RLS-политик составляют менее 1–2% при наличии композитных индексов `(tenant_id, id)`.
*   **Ограничение пула:** Необходимо контролировать, чтобы транзакции всегда сбрасывали локальные сессионные переменные при возврате соединения в пул `sqlx` (решается использованием `SET LOCAL` вместо `SET`, что автоматически очищает контекст при завершении транзакции).
