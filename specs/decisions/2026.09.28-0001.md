# Тема: Выбор паттерна Shared Schema с PostgreSQL RLS для Strict Multi-tenancy

## Контекст и постановка проблемы

Для реализации Enterprise-grade LMS-платформы требуется жесткая изоляция данных (Strict Multi-tenancy) между независимыми организациями (тенантами). Платформа должна поддерживать динамическое создание новых тенантов через API (динамический provisioning) без простоя системы и ручного вмешательства администратора.

Ключевые ограничения:

* **Динамический provisioning** — создание тенанта через API за одну транзакцию, без DDL-операций, влияющих на другие тенанты.
* **Единый пул соединений** — асинхронный бэкенд на Rust (Axum) работает через общий пул `sqlx`. Подготовленные запросы (Prepared Statements) должны переиспользоваться между запросами разных тенантов.
* **Единый процесс миграций** — обновление схемы СУБД не должно масштабироваться по числу тенантов.
* **Требования NFR** — SLA, RTO/RPO, лимиты (см. [`../NFR.md`](../NFR.md)).

Рассматривались два архитектурных паттерна на уровне СУБД PostgreSQL.

## Драйверы решения (Decision Drivers)

* Стоимость динамического provisioning тенанта — должна быть O(1), а не O(число тенантов).
* Совместимость с асинхронным пулом `sqlx` и переиспользование Prepared Statements.
* Стоимость миграций СУБД — единая, независимая от числа тенантов.
* Устойчивость к логическим ошибкам прикладного кода (забыли `WHERE tenant_id = …`).
* Совместимость с RLS-политиками и требованиями по производительности (< 2% накладных расходов).

## Рассмотренные варианты и трейд-оффы (Trade-offs)

### Вариант 1: Isolated Schemas (Изолированные схемы)

* **Плюсы:**
  * Максимальная ментальная изоляция на уровне таблиц.
  * Проще делать резервное копирование и очистку данных отдельного клиента.
  * Отсутствие риска «забыли `WHERE tenant_id`» на уровне СУБД — данные физически лежат в разных схемах.
* **Минусы:**
  * Экстремальное усложнение миграций СУБД: при обновлении платформы нужно накатывать миграции на тысячи схем параллельно. Это либо долго, либо требует отдельной инфраструктуры миграций.
  * Резкая деградация пула соединений `sqlx`: либо отдельные пулы к каждой схеме (взрыв по числу соединений), либо динамическое переключение `search_path` (сбрасывает кэш Prepared Statements).
  * Динамический provisioning тенанта превращается в DDL-операцию (`CREATE SCHEMA`, `CREATE TABLE ...` для десятков таблиц), что несовместимо с требованием O(1) и не транзакционно в общем случае.

### Вариант 2: Shared Schema с Row-Level Security (RLS)

* **Плюсы:**
  * Идеально ложится на концепцию асинхронного бэкенда на Rust: один пул соединений, переиспользование Prepared Statements.
  * Динамический provisioning тенанта — мгновенная транзакция `INSERT INTO tenants ...`.
  * Единый и предсказуемый процесс миграции СУБД: одна миграция на весь кластер.
  * Изоляция данных обеспечивается на уровне ядра СУБД, а не прикладного кода: даже при логической ошибке в `WHERE` СУБД не вернёт строки чужого тенанта.
* **Минусы:**
  * Риск логической ошибки в коде бэкенда, которая может привести к утечке данных, если в сессии не установлен `app.current_tenant_id` (митигируется: политика RLS возвращает пустой результат, а не чужие строки, — fail-safe).
  * Накладные расходы на валидацию RLS-политик (митигируется композитными индексами `(tenant_id, id)`).

## Принятое решение

Утвержден **Вариант 2: Shared Schema с Row-Level Security (RLS)**.

Изоляция переносится с уровня прикладных SQL-запросов на уровень ядра СУБД PostgreSQL:

1. Для всех таблиц тенантов принудительно включается RLS: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`.
2. Создается единая сквозная политика, которая аппаратно отсекает строки, не соответствующие локальному сессионному параметру `app.current_tenant_id`:

   ```sql
   CREATE POLICY tenant_isolation_policy ON <table_name>
       USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid);
