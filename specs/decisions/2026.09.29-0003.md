# Тема: Подпись, верификация и kill switch для WASM-плагинов Контура Б

## Контекст и постановка проблемы

Платформа исполняет верифицированные плагины Контура Б напрямую в адресном пространстве клиентской части Leptos (см. [`../PLUGIN.md`](../PLUGIN.md) §2.2). Такие модули имеют прямой доступ к памяти фронтенда, к локальному хранилищу IndexedDB и к JavaScript-мостам Ядра. Это даёт максимальную производительность и полноценный offline-first, но одновременно создаёт три класса рисков:

1. **Компрометация артефакта** — подмена `.wasm`-файла в DAM-хранилище или при передаче по сети.
2. **Ошибка в процессе верификации** — если подпись не проверяется, платформа исполняет произвольный код с правами Ядра.
3. **Уже закэшированный плагин** — если после релиза в плагине обнаружена уязвимость, недостаточно запретить новые загрузки: `.wasm` уже лежит в Service Worker-кэше у тысяч клиентов.

Спецификация процесса зафиксирована в [`../PLUGIN.md`](../PLUGIN.md) §7 (проектное решение). Настоящий ADR фиксирует финальный выбор алгоритма, формата, стратегии ротации ключа и политики поведения при отсутствии сети.

## Драйверы решения (Decision Drivers)

* **Безопасность.** Исполнение недоверенного кода в одном адресном пространстве с Ядром недопустимо без криптографической верификации.
* **Управляемость.** Возможность экстренно отозвать скомпрометированный плагин без обновления клиента.
* **Офлайн-совместимость.** Платформа позиционируется как Offline-First; политика отзыва не должна ломать офлайн-сценарии.
* **Производительность.** Проверка подписи не должна добавлять существенную задержку к монтированию плагина (бюджет — в [`../NFR.md`](../NFR.md) §8).
* **Криптографическая стойкость.** Алгоритм должен соответствовать современным стандартам (Ed25519).

## Рассмотренные варианты и трейд-оффы (Trade-offs)

### Вариант 1: Без подписи, только ACL на уровне DAM

* **Плюсы:** простота, нулевые накладные расходы.
* **Минусы:** компрометация DAM = компрометация всех клиентов. Не соответствует Enterprise-требованиям.

### Вариант 2: Подпись Ed25519, Revocation List, fail-open при отсутствии сети

* **Плюсы:**
  * криптографическая стойкость Ed25519;
  * проверка подписи выполняется браузерным WebCrypto без дополнительных зависимостей в WASM-бандле;
  * Revocation List позволяет отзывать плагины без обновления клиента;
  * fail-open сохраняет офлайн-работу.
* **Минусы:**
  * при устаревшем Revocation List (нет сети долго) компрометированный плагин может быть запущен;
  * требуется отдельная инфраструктура хранения release-ключа (Vault/KMS).

### Вариант 3: Подпись Ed25519 + strict revocation (fail-closed при отсутствии свежего списка)

* **Плюсы:**
  * максимальная безопасность: плагин Контура Б не запускается без свежего Revocation List.
* **Минусы:**
  * ломает офлайн-сценарии: в самолёте/метро плагины не будут работать;
  * противоречит концепции Offline-First.

## Принятое решение

Выбран **Вариант 2: подпись Ed25519, Revocation List, fail-open по умолчанию, опциональный strict revocation на уровне тенанта.**

1. **Алгоритм:** Ed25519 (`ed25519-dalek` в Rust, WebCrypto Ed25519 в браузере). Хэш артефакта — SHA-256.
2. **Формат артефакта подписи:** `.wasm.sig` рядом с `.wasm` в DAM-хранилище. Содержит: подпись Ed25519, версию плагина, дату подписи, идентификатор релиза.
3. **Кто подписывает:** платформа. Release-ключ хранится исключительно в `nexus-vault` (см. [`../DEPLOY.md`](../DEPLOY.md) §3); сторонние разработчики доступа не имеют.
4. **Верификация:** при монтировании Контура Б клиент скачивает `.wasm` и `.wasm.sig`, вычисляет SHA-256 от бинарного тела `.wasm`, проверяет подпись через WebCrypto. При провале — плагин не монтируется, событие пишется в `audit_log` с `%reason = 'signature_mismatch'`.
5. **Revocation List:** список `plugin_id` (или конкретных версий), запуск которых запрещён. Отдаётся клиенту при инициализации PWA, периодически при активной сессии, и перед монтированием (если есть сеть).
6. **Поведение при отзыве:**
   * В онлайне — удаление артефактов из Service Worker-кэша, `cached_content` и `offline_plugin_state`.
   * В офлайне — используется последняя известная версия Revocation List. Если `plugin_id` в ней числится — блокировка. Если версия устарела и `plugin_id` не числится — плагин может запуститься (осознанный риск fail-open).
   * **Strict revocation** — опция тенанта: при отсутствии свежего Revocation List (старше N часов) Контур Б вообще не монтируется. Рекомендуется для Enterprise с повышенными требованиями безопасности.
7. **Ротация release-ключа:** поддерживается двойной комплект (старый + новый публичный ключ) на переходный период. Период переходной ротации — 90 дней; по истечении — старый ключ удаляется.

## Последствия и риски

* **Безопасность:** компрометация DAM не даёт исполнения произвольного кода; компрометация release-ключа требует явного решения о ротации.
* **Производительность:** проверка Ed25519 не должна добавлять более 30 мс к p95 монтирования Контура Б (см. [`../NFR.md`](../NFR.md) §8).
* **Эксплуатация:** Revocation List — отдельный артефакт, требует инфраструктуры доставки (эндпоинт в `OPEN_API.md` + кэш на клиенте).
* **Риски и митигация:**
  * **Риск:** release-ключ скомпрометирован. **Митигация:** хранение в Vault, ротация, аудит доступа.
  * **Риск:** клиент долго не был в сети и пропустил отзыв. **Митигация:** strict revocation для критичных тенантов.
  * **Риск:** Revocation List можно подделать. **Митигация:** Revocation List подписывается тем же release-ключом, что и `.wasm.sig`; клиент проверяет подпись списка при получении.
