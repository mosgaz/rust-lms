# Тема: Выбор OTel backend для SaaS-поставки

## Контекст и постановка проблемы

Платформа использует OpenTelemetry как стандарт наблюдаемости (см. [`../DIAGNOSTICS.md`](../DIAGNOSTICS.md) §4). Инструментирование и OTLP-экспорт зафиксированы; сервис `rust-lms-otel-collector` добавлен в `docker-compose` (см. [`../DEPLOY.md`](../DEPLOY.md) §3). Однако **backend для хранения трейсов** не выбран. В On-Premise это решение на стороне заказчика; в SaaS-поставке платформа обязана предоставить один из поддерживаемых backend'ов по умолчанию.

Без фиксированного backend'а:

* трейсы негде хранить в SaaS-контуре;
* невозможно предъявлять SLA на наблюдаемость;
* интеграция с внешними BI/SIEM не определена.

## Драйверы решения (Decision Drivers)

* **Совместимость с OTLP.** Backend должен нативно принимать OTLP/gRPC.
* **Self-hosted.** Возможность развертывания в закрытом контуре (Air-gapped).
* **Стоимость.** Не должно быть vendor lock-in; стоимость хранения трейсов — предсказуемая.
* **Интеграция с метриками.** Возможность использовать один стек для трейсов и метрик (Prometheus / OTLP-metrics).
* **Зрелость.** Backend должен иметь активное сообщество и production-кейсы.

## Рассмотренные варианты и трейд-оффы (Trade-offs)

### Вариант 1: Grafana Tempo

* **Плюсы:**
  * нативно принимает OTLP;
  * self-hosted;
  * отлично интегрируется с Grafana, Prometheus, Loki (единый стек);
  * эффективное хранение (партиционирование по времени, S3-совместимое хранилище).
* **Минусы:**
  * без Grafana UI — ограниченный UX (трейсы неудобно искать без Grafana);
  * для полноценного использования требуется развернуть стек Grafana (Loki + Tempo + Prometheus).

### Вариант 2: Jaeger

* **Плюсы:**
  * исторически первый OTel-совместимый backend;
  * собственная UI из коробки;
  * self-hosted.
* **Минусы:**
  * UI уступает Grafana по функциональности;
  * хранение только в Cassandra/Elasticsearch — сложнее в эксплуатации;
  * проект в стадии «maintenance» (архитектурный комитет CNCF рекомендует Tempo).

### Вариант 3: OpenSearch (с OTel-плагином)

* **Плюсы:**
  * если тенант уже использует OpenSearch для логов, единый стек;
  * мощный поиск и аналитика.
* **Минусы:**
  * тяжелее в эксплуатации;
  * OTel-интеграция слабее, чем у Tempo/Jaeger.

### Вариант 4: SaaS (Datadog, New Relic, Honeycomb)

* **Плюсы:** минимальные эксплуатационные затраты.
* **Минусы:** не работает в Air-gapped; vendor lock-in; трансграничная передача трейсов (может нарушать Data Residency, см. ADR-0005).

## Принятое решение

Выбран **Вариант 1: Grafana Tempo** как backend для SaaS-поставки по умолчанию.

1. **SaaS-поставка:** Tempo разворачивается внутри контура платформы; хранение трейсов — в S3-совместимом хранилище (MinIO или облачный S3).
2. **On-Premise:** заказчик выбирает backend самостоятельно из списка поддерживаемых (Tempo, Jaeger, OpenSearch). `rust-lms-otel-collector` маршрутизирует трейсы в выбранный backend.
3. **Air-gapped:** Tempo разворачивается локально, экспорт во внешние SaaS запрещён.
4. **UI:** Grafana разворачивается как часть SaaS-стека; для On-Premise — по требованию.
5. **Семплирование:** head-based 10% + tail-based 100% для ошибок и медленных трейсов — конфигурируется в OTel Collector (см. [`../DIAGNOSTICS.md`](../DIAGNOSTICS.md) §4.3).
6. **Метрики:** Prometheus (уже стандарт де-факто в Rust-экосистеме); экспорт через OTLP-metrics или напрямую в Prometheus scrape endpoint.

### Что НЕ выбираем и почему

* **Jaeger** — отклонён из-за статуса «maintenance» и более слабой интеграции с метриками.
* **OpenSearch** — отклонён как основной вариант; остаётся опцией для тенантов, уже использующих OpenSearch.
* **SaaS** — отклонён для SaaS-поставки платформы из-за несовместимости с Air-gapped и Data Residency.

## Последствия и риски

* **Эксплуатация:** требуется развернуть стек Grafana (Tempo + Loki + Prometheus). В SaaS — часть инфраструктуры; в On-Premise — опционально.
* **Стоимость:** хранение трейсов в S3-совместимом хранилище; стоимость предсказуема и линейна.
* **Data Residency:** Tempo и хранилище трейсов размещаются в том же регионе, что и данные тенанта (см. ADR-0005).
* **Риски и митигация:**
  * **Риск:** сложность эксплуатации полного стека Grafana. **Митигация:** SaaS-стек управляется платформой; On-Premise — опционально.
  * **Риск:** рост стоимости хранения трейсов. **Митигация:** tail-based семплирование; retention для трейсов — 30 дней по умолчанию.
  * **Риск:** vendor lock-in на Grafana. **Митигация:** OTLP-совместимость позволяет сменить backend без изменений в инструментировании.
