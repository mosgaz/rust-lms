# Тема: Операционный регламент deprecation версий API

## Контекст и постановка проблемы

Политика версионирования API зафиксирована в [`../OPEN_API.md`](../OPEN_API.md) §5: major-версия в URL, RFC 8594 (`Deprecation`, `Sunset`, `Link`), график T+0 / T+6 / T+12, событие `api.deprecation.announced`. Однако **операционный регламент** — кто, когда, через какой инструмент инициирует deprecation, как проверяется отсутствие активных вызовов перед sunset — не зафиксирован.

Без регламента deprecation превращается в ad-hoc операцию: либо забывается, либо выполняется без должного уведомления интеграторов, либо откладывается на неопределённый срок.

## Драйверы решения (Decision Drivers)

* **Предсказуемость.** Интеграторы должны точно знать, когда и как будет объявлен deprecation.
* **Безопасность.** Нельзя удалить версию, если её ещё активно используют.
* **Минимизация ручной работы.** Процесс должен быть по возможности автоматизирован.
* **Аудит.** Каждое решение о deprecation фиксируется с обоснованием.
* **Совместимость с On-Premise.** Заказчик может отказаться от удаления версии.

## Рассмотренные варианты и трейд-оффы (Trade-offs)

### Вариант 1: Ручной процесс без формализации

* **Плюсы:** гибкость.
* **Минусы:** решения зависят от конкретных людей, забываются, теряются в переписках.

### Вариант 2: Формализованный процесс с ADR + чек-листом

* **Плюсы:**
  * каждое решение о deprecation фиксируется ADR (кто, что, почему);
  * чек-лист гарантирует, что ни один шаг не пропущен;
  * автоматизация отдельных шагов (вебхук, письмо, заголовки).
* **Минусы:** требует дисциплины; на ранних стадиях (пока API мало используется) может казаться избыточным.

### Вариант 3: Полная автоматизация (CI-пайплайн для deprecation)

* **Плюсы:** минимум ручной работы.
* **Минусы:** сложно реализовать; требует инфраструктуры; преждевременно для MVP.

## Принятое решение

Выбран **Вариант 2: формализованный процесс с ADR + чек-листом.**

### Кто инициирует

* **Product owner платформы** — инициирует решение о deprecation, обосновывает.
* **Архитектурный комитет** — утверждает ADR о deprecation.
* **Команда платформы** — выполняет техническую часть (заголовки, вебхук, миграционный гайд).

### Формат фиксации

* **ADR** — «Deprecation of API vN» с обоснованием, датой `Sunset`, ссылкой на migration guide.
* **Запись в [`../CHANGELOG.md`](../../CHANGELOG.md)** — с указанием версии, даты sunset и ссылки.

### Чек-лист объявления deprecation

1. **ADR утверждён** архитектурным комитетом.
2. **Migration guide** подготовлен и опубликован (домен или внутренняя wiki).
3. **Заголовки RFC 8594** добавлены во все ответы deprecated-версии:
   * `Deprecation: @<unix_timestamp>`
   * `Sunset: <HTTP-date>`
   * `Link: <migration-guide-url>; rel="deprecation"`
4. **Событие `api.deprecation.announced`** отправлено всем подписчикам тенанта, у которых зарегистрирован вебхук на это событие.
5. **Письмо администратору тенанта** отправлено на email владельца организации.
6. **In-app уведомление** в `cpanel` для администраторов тенанта.
7. **Запись в CHANGELOG** опубликована.
8. **Повторное уведомление** (вебхук + письмо) через 6 месяцев (T+6).
9. **Финальный гайд** по миграции опубликован к T+6.

### Перед Sunset (T+12)

1. **Проверка активности через OTel-метрики** (см. [`../DIAGNOSTICS.md`](../DIAGNOSTICS.md) §4): все вызовы deprecated-версии за последние 30 дней.
2. **Если активные вызовы есть:**
   * связаться с конкретными тенантами-пользователями;
   * либо продлить Sunset (с обоснованием в ADR);
   * либо принудительно отключить (последний вариант — только с явного решения архитектурного комитета).
3. **Если активных вызовов нет:**
   * отключить версию;
   * все запросы к ней возвращают `410 Gone` с телом, содержащим ссылку на актуальную версию;
   * запись в CHANGELOG.

### On-Premise-особенности

* Для On-Premise поставок платформа не может принудительно удалить версию на изолированном контуре заказчика.
* Deprecation версии для On-Premise фиксируется в релиз-нотах; удаление — на усмотрение заказчика.
* Air-gapped-инсталляции не получают вебхук `api.deprecation.announced` — уведомление только через релиз-ноты и документацию.

## Последствия и риски

* **Процесс:** каждое решение о deprecation фиксируется ADR — история решений сохраняется.
* **Автоматизация:** отдельные шаги (заголовки, вебхук, письмо) могут быть автоматизированы в дальнейшем (Вариант 3).
* **Риски и митигация:**
  * **Риск:** процесс забыли выполнить. **Митигация:** чек-лист в ADR обязателен; CI-проверка наличия заголовков RFC 8594 для deprecated-версий.
  * **Риск:** пропустили активных пользователей. **Митигация:** проверка активности через OTel-метрики перед Sunset.
  * **Риск:** On-Premise-заказчик не обновился. **Митигация:** уведомление в релиз-нотах; поддержка deprecated-версии по контракту.
