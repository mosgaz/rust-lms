# Тема: Формат и enforcement лицензионного ключа для коробочных поставок

## Контекст и постановка проблемы

Платформа поставляется в двух режимах: SaaS (управляемый сервис) и On-Premise / Air-gapped (коробочная поставка). Для коробочной поставки вендор должен ограничивать функционал и масштаб в соответствии с коммерческим соглашением: количество тенантов, пользователей, плагинов, доступ к отдельным функциям (ALE, SCIM, DRM, SCORM 2004 Sequencing).

Ключевые ограничения:

* В Air-gapped отсутствует внешняя сеть — лицензия должна валидироваться **локально**, без вызовов к вендору.
* Заказчик может переносить платформу на новый сервер (или в новый кластер) — лицензия должна перевыпускаться без потери данных.
* Платформа не должна «отключаться моментально» при истечении лицензии — заказчик должен сохранять доступ к своим данным.
* Формат ключа должен быть криптографически стойким (невозможность подделки или редактирования).

Спецификация лицензирования зафиксирована в [`../LICENSING.md`](../LICENSING.md). Настоящий ADR фиксирует финальный выбор формата, типа binding, политики enforcement и grace period.

## Драйверы решения (Decision Drivers)

* **Офлайн-валидация.** Никаких внешних вызовов в Air-gapped.
* **Криптографическая стойкость.** Ed25519 — стандарт, согласованный с ADR-0003 (подпись плагинов).
* **Гибкость привязки.** Три сценария: одиночный сервер, домен, кластер.
* **Прозрачность.** Администратор заказчика видит статус и потребление.
* **Мягкая деградация.** Grace period и запрет на удаление данных.
* **Ротация при смене hardware.** Без потери данных.

## Рассмотренные варианты и трейд-оффы (Trade-offs)

### Вариант 1: Онлайн-валидация через API вендора

* **Плюсы:** вендор полностью контролирует активацию; можно отзывать лицензии.
* **Минусы:** невозможен в Air-gapped; зависимость от доступности сервиса вендора; несовместим с моделью коробочной поставки.

### Вариант 2: Лицензионный файл с криптографической подписью (JWT-подобный, офлайн-валидация)

* **Плюсы:**
  * работает в Air-gapped;
  * криптографическая стойкость (Ed25519);
  * можно перевыпускать без внешних вызовов;
  * единый алгоритм с подписью WASM-плагинов (ADR-0003).
* **Минусы:**
  * вендор не может отозвать лицензию «в моменте»;
  * требуется перевыпуск при смене hardware.

### Вариант 3: Гибрид — офлайн-ключ + периодический онлайн-heartbeat (только для SaaS/On-Premise без Air-gapped)

* **Плюсы:** комбинирует офлайн-гибкость и онлайн-контроль.
* **Минусы:** усложняет логику; не работает в Air-gapped; для SaaS и так управляется иначе.

## Принятое решение

Выбран **Вариант 2: офлайн-ключ с криптографической подписью.**

1. **Алгоритм:** Ed25519 (тот же, что для `.wasm.sig` плагинов — см. ADR-0003). Хэш — SHA-256.
2. **Формат:** JWT-подобный токен (`<header>.<payload>.<signature>`, base64url).
3. **Типы привязки:**
   * **`node_locked`** — SHA-256 от CPU ID + MAC-адрес primary NIC + серийный номер диска. Рекомендуется для одиночного сервера.
   * **`domain_locked`** — FQDN внутреннего домена заказчика. Для On-Premise с несколькими узлами.
   * **`floating`** — без привязки к hardware, но с ограничением на количество активных инстансов через внутренний heartbeat. Для кластеров.
4. **Enforcement:**
   * **Soft** — в пределах срока и grace period: ограничения применяются только при превышении лимитов.
   * **Hard** — после grace period: read-only для новых операций; данные не удаляются; аутентификация, чтение, экспорт и сбор xAPI продолжают работать.
5. **Grace period:** 30 дней по умолчанию, конфигурируется вендором в payload.
6. **Хранение:** таблица `license` (глобальная, вне RLS), single-row.
7. **API:** `GET /api/v1/internal/license` для чтения статуса; `POST /api/v1/internal/license` для установки (только On-Premise). В Air-gapped — CLI `rust-lms-license`.
8. **Ротация:** при смене hardware вендор выпускает новый ключ с тем же `license_id` и новым `hardware_id`; администратор устанавливает через CLI.

## Последствия и риски

* **Безопасность:** подделка ключа требует компрометации приватного ключа вендора. Аналогично ADR-0003.
* **Эксплуатация:** заказчик может перевыпустить лицензию без потери данных. Процесс требует ручного взаимодействия с вендором (передача hardware ID → выпуск → установка).
* **UX:** при истечении лицензии администратор видит баннер, заказчик получает вебхук `license.grace_started`.
* **Риски и митигация:**
  * **Риск:** потеря hardware ID при миграции. **Митигация:** процедура ротации описана в [`../LICENSING.md`](../LICENSING.md) §9.
  * **Риск:** отзыв лицензии в моменте невозможен. **Митигация:** для SaaS лицензия не используется; для On-Premise отзыв — через перевыпуск с коротким сроком.
  * **Риск:** пользователь обходит лимит, добавляя пользователей через SCIM или ETL. **Митигация:** все операции создания пользователей проходят через общий счётчик `current_usage`; превышение лимита блокируется на уровне API.
  * **Риск:** floating-лицензия допускает превышение числа инстансов при сетевой изоляции кластера. **Митигация:** heartbeat внутри кластера; при потере связи между узлами платформа деградирует к `node_locked`-поведению.
