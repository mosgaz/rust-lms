# Тема: Выбор СУБД для слоя LRS (Аналитика xAPI)

## Контекст и постановка проблемы

Платформа `rust-lms` спроектирована как высокопроизводительная модульная LMS корпоративного уровня. Слой **LRS (Learning Record Store)** отвечает за сбор, хранение и аналитическую обработку неизменяемых логов активности студентов и телеметрии прокторинга по стандарту **xAPI (JSON-LD структуры)**.

### Целевые метрики одной инсталляции:
*   **MAU (Monthly Active Users):** ~5 000 пользователей (с потенциалом масштабирования до 10 000 – 20 000 на пике).
*   **Характер нагрузки:** Интенсивная запись (Write-Heavy) потока данных прокторинга и кликстрима в моменты массовых экзаменов/тестирований с последующей агрегацией для построения отчетов.
*   **Среда развертывания:** Поддержка как облачных SaaS-сред, так и изолированных закрытых контуров (On-Premise / Air-gapped инсталляции) на ограниченных аппаратных мощностях с жесткими требованиями нормативного регулирования.

---

## 2. Сравнительный анализ альтернатив

Рассматривались два архитектурных варианта, заложенных в спецификации `specs/DB_SCHEMA.md`:

### Вариант А: TimescaleDB (Расширение PostgreSQL)
Реляционная СУБД с автоматическим секционированием таблиц по времени (гипертаблицы).

*   **Плюсы:**
    *   **Единый технологический стек:** Работает внутри основной БД платформы (PostgreSQL 15+). Нет необходимости администрировать, мониторить и бэкапить вторую СУБД.
    *   **Нативный Multi-tenancy (RLS):** Полная совместимость со строгими политиками Row-Level Security на уровне ядра СУБД. Настройки изоляции тенантов переиспользуются автоматически.
    *   **Упрощение Rust-кода:** Запросы и миграции пишутся через уже подключенный compile-time драйвер `sqlx`.
    *   **Низкий TCO:** Минимальное потребление памяти, идеальное соответствие для серверов с ограниченными ресурсами в Air-gapped средах.
*   **Минусы:** Более слабое сжатие данных и меньшая скорость агрегации на объемах свыше 100 млн строк по сравнению с колоночными СУБД.

### Вариант Б: ClickHouse (Выделенный OLAP-кластер)
Поколоночная аналитическая СУБД.

*   **Плюсы:** Экстремальное сжатие колонок (до 10 раз), колоссальная скорость обработки миллиардов строк.
*   **Минусы:** Высокий порог входа, колоссальный DevOps-overhead (требует выделенных серверов, сложной координации кластера), отсутствие нативного RLS (изоляцию тенантов нужно гарантировать на уровне прикладного кода Rust). При нагрузке до 20 000 MAU является классическим примером **Overengineering**.

---

## 3. Решение

**Утвердить Вариант А (TimescaleDB) в качестве приоритетной СУБД для слоя LRS.**

При масштабе инсталляции в 5 000 – 20 000 MAU производительности TimescaleDB на базе одной ноды PostgreSQL более чем достаточно для покрытия пиковых нагрузок (в пределах 500–1000 xAPI-инсертов в секунду) без усложнения инфраструктуры разработки и эксплуатации.

## 4. Инструкция по интеграции в структуру проекта

Для фиксации решения необходимо внесить изменения в кодовую базу и файлы документации.

### Шаг A. Обновление документа `specs/README.md` или `specs/DB_SCHEMA.md`
Замените раздел, описывающий архитектуру LRS, следующим текстом:

```markdown
### § 2.5 Аналитическое хранилище (LRS)
В качестве рантайма для хранения xAPI-логов утверждена **TimescaleDB** (Вариант А). 
Использование ClickHouse (Вариант Б) признано избыточным для текущего масштаба инсталляций (до 20 000 MAU) 
и заморожено до достижения платформой объема данных >100 млн записей в месяц.
Изоляция данных организаций в LRS обеспечивается нативно через PostgreSQL Row-Level Security (RLS).
```

### Шаг B. Шаблон SQL-миграции для `sqlx` (`crates/api/migrations/`)
Создайте файл миграции (например, `20261006000000_init_lrs_timescale.sql`):

```sql
-- 1. Включаем расширение TimescaleDB (должно быть доступно в образе СУБД)
CREATE EXTENSION IF NOT EXISTS timescaledb CASCADE;

-- 2. Создаем таблицу xAPI логов
CREATE TABLE xapi_statements (
    id UUID NOT NULL,
    tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    timestamp TIMESTAMPTZ NOT NULL,
    actor_identity_id UUID NOT NULL,
    verb VARCHAR(64) NOT NULL,
    object_id VARCHAR(255) NOT NULL,
    payload JSONB NOT NULL,
    PRIMARY KEY (id, timestamp) -- В TimescaleDB составной ключ обязан включать колонку времени
);

-- 3. Превращаем таблицу в гипертаблицу с секционированием по 7 дней
SELECT create_hypertable('xapi_statements', 'timestamp', chunk_time_interval => INTERVAL '7 days');

-- 4. Внедряем принудительную RLS-изоляцию тенантов
ALTER TABLE xapi_statements ENABLE ROW LEVEL SECURITY;

CREATE POLICY xapi_tenant_isolation ON xapi_statements
    USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid);

-- 5. Индекс для быстрой аналитики внутри тенанта
CREATE INDEX idx_xapi_analytics ON xapi_statements (tenant_id, verb, object_id);
```

## 5. Последствия решения

*   **Для разработчиков:** Код работы с LRS остается в рамках крейта `crates/api` с использованием макросов `sqlx::query!`. Нет необходимости внедрять сторонние библиотеки и управлять двумя разными пулами подключений.
*   **Для DevOps/Deployment:** Спецификация `specs/docker-compose.yml` упрощается. Образ `postgres:15` заменяется на официальный образ `timescale/timescaledb:latest-pg15`. Дополнительные контейнеры для ClickHouse не требуются.
*   **Для безопасности:** Аудит безопасности упрощается, так как все данные платформы (и реляционные, и аналитические) защищены единым механизмом PostgreSQL RLS, что упрощает соответствие требованиям ФСТЭК России.
