# Тема: Data Residency: процедура миграции тенанта между регионами

## Контекст и постановка проблемы

Платформа поддерживает SaaS-поставку с явным фиксированием региона размещения данных тенанта (Core-БД, LRS, DAM, бэкапы, KMS). В [`../STANDARDS.md`](../STANDARDS.md) §«Data Residency и суверенитет данных» зафиксировано, что миграция тенанта между регионами — **не автоматическая** процедура с аудитом. Сам регламент миграции отсутствует.

Типичные триггеры миграции:

* изменение регуляторных требований (например, тенант начинает обрабатывать ПДн граждан РФ и должен переехать в РФ-регион);
* оптимизация стоимости (тенант переезжает в регион с более дешёвой инфраструктурой);
* организационные причины (поглощение, разделение бизнеса).

Без формализованного регламента миграция рискует превратиться в ad-hoc операцию с потерей данных и нарушением Data Residency.

## Драйверы решения (Decision Drivers)

* **Целостность данных.** Миграция не должна терять или повреждать данные.
* **Непрерывность сервиса.** Минимизация downtime для тенанта.
* **Аудит.** Каждый шаг миграции фиксируется в `audit_log`.
* **Data Residency.** Данные не должны «проходить транзитом» через регионы, где их хранение запрещено.
* **KMS-совместимость.** Ключи ALE (см. ADR-0004) должны быть перенесены или перевыпущены.

## Рассмотренные варианты и трейд-оффы (Trade-offs)

### Вариант 1: Dump & Restore с downtime

* **Плюсы:** простота, полный контроль над процессом.
* **Минусы:** downtime тенанта (часы или дни), риск рассинхронизации при активной работе.

### Вариант 2: Logical replication + постепенный переезд

* **Плюсы:** минимальный downtime, потоковая миграция.
* **Минусы:** сложность, требует поддержки на уровне инфраструктуры, ограничения по LRS (TimescaleDB/ClickHouse).

### Вариант 3: Гибрид — dump для DAM/LRS + logical replication для Core-БД

* **Плюсы:**
  * DAM и LRS — иммутабельные/архивные данные, dump-restore допустим;
  * Core-БД — активные данные, logical replication даёт минимальный downtime.
* **Минусы:** сложнее, чем Вариант 1, но оправдано активной работой тенанта.

## Принятое решение

Выбран **Вариант 3: гибридная процедура.**

### Процедура миграции

1. **Подготовка (T-7 дней):**
   * ADR фиксирует миграцию и её причину.
   * Уведомление администратора тенанта за 7 дней (см. [`../OPEN_API.md`](../OPEN_API.md) §4.1 — новое событие `tenant.migration.scheduled`).
   * Создание целевого региона-инфраструктуры (Core-БД, LRS, DAM, Vault).
2. **Инициализация (T-1 день):**
   * Перевод тенанта в режим **read-only** на источнике (мутации отклоняются с `423 Locked`).
   * Финальная проверка целостности источника.
3. **Перенос данных (T-0):**
   * **Core-БД:** dump-restore или logical replication (в зависимости от размера).
   * **LRS (TimescaleDB / ClickHouse):** dump партиций по `tenant_id` за последние N дней + архивация холодных партиций.
   * **DAM:** синхронизация bucket через `rclone` / `mc mirror` (S3-совместимый).
   * **Vault:** KEK и DEK миграции **не переносятся** — они перевыпускаются в целевом регионе, данные перешифровываются (в противном случае ключ пересекает границу региона, что противоречит Data Residency). Для тенантов без ALE — шаг пропускается.
4. **Валидация (T+0 … T+1):**
   * Контрольные суммы по Core-БД (количество строк по таблицам).
   * Контрольные суммы по DAM (количество объектов, общий размер).
   * Проверка LRS: количество statements за период.
   * **Только после успешной валидации** источник помечается как готовый к удалению.
5. **Переключение (T+1):**
   * DNS / routing переводятся на целевой регион.
   * Тенант выводится из read-only.
   * Событие `tenant.migration.completed` в вебхуках.
6. **Очистка источника (T+30 дней):**
   * Источник переводится в режим архива.
   * Через 30 дней данные источника удаляются (с фиксацией в `audit_log`).
   * Бэкапы источника хранятся ещё 90 дней, затем удаляются.

### Ограничения

* Миграция выполняется вручную (не автоматизирована) и контролируется архитектурным комитетом.
* Миграция затрагивает только один тенант за раз.
* Для Air-gapped On-Premise миграция между регионами не применима — регион фиксирован инфраструктурой заказчика.
* Миграция LRS в Варианте Б (ClickHouse) требует дополнительной проработки (партиционирование по `tenant_id` и время).

## Последствия и риски

* **Downtime:** минимизируется до 1–2 суток для крупных тенантов; для мелких — часы.
* **Безопасность:** перевыпуск ключей ALE исключает трансграничную передачу ключевого материала.
* **Аудит:** каждое действие фиксируется в `audit_log` с `%tenant_id`, `%migration_id`, `%step`.
* **Риски и митигация:**
  * **Риск:** частичная миграция, потеря данных. **Митигация:** валидация до удаления источника; источник хранится 30 дней.
  * **Риск:** рассинхронизация при переключении. **Митигация:** read-only на источнике перед переносом.
  * **Риск:** утечка KEK через лог. **Митигация:** KEK никогда не логируется, только идентификаторы ключей.
