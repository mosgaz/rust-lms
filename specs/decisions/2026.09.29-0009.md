# Тема: Архитектура управления функциональными флагами (Feature Flags)

## Контекст и постановка проблемы

Для безопасного поэтапного релиза (rollout) новых функций (SCIM, ВКС, ALE, offline-first, Conformance Testing) и проведения закрытых бета-тестов платформе необходим механизм функциональных флагов (Feature Flags).

Платформа уже использует систему лицензирования ([`2026.09.29-0008.md`](2026.09.29-0008.md)), где `license.features` определяет **коммерческое право** тенанта на использование функции. Возникла необходимость чётко разделить:

* **Право на использование** (`license.features`) — что тенант купил.
* **Операционную доступность** (`feature_flags`) — включена ли функция прямо сейчас (для beta-теста, безопасного rollout, временного отключения).

Дополнительное требование: архитектура **не должна вводить новые внешние зависимости** (Redis, Consul, Unleash-сервер) для минимизации сложности развёртывания в Air-gapped средах. Платформа должна работать на минимальном наборе сервисов (PostgreSQL, DAM, Vault).

Дополнительные связи:

* `tenant_feature_flags` защищена тем же RLS-механизмом, что и остальные данные тенанта — см. ADR [`2026.09.28-0001.md`](2026.09.28-0001.md).
* В будущем feature flags могут управлять доступностью отдельных WASM-плагинов (например, `enable_plugin_xyz`), что связано с механизмом Revocation List — см. ADR [`2026.09.29-0003.md`](2026.09.29-0003.md).

## Драйверы решения (Decision Drivers)

* **Безопасный поэтапный rollout** — возможность включить функцию для одного тенанта без релиза.
* **Отсутствие новых внешних зависимостей** — критично для Air-gapped поставок.
* **Транзакционность и аудит** — изменения флагов должны попадать в `audit_log`.
* **Производительность** — проверка флага не должна добавлять latency к запросам (O(1) в памяти).
* **Разграничение права и состояния** — лицензия и флаги решают разные задачи.
* **Делегирование** — некоторые флаги тенант-админ должен уметь переключать сам, некоторые — только супер-админ.

## Рассмотренные варианты и трейд-оффы (Trade-offs)

### Вариант 1: Только `license.features` (без feature flags)

* **Плюсы:** простота, один источник истины.
* **Минусы:** невозможно включить функцию для одного тенанта без релиза; невозможно провести закрытый beta-тест; любое изменение требует перевыпуска лицензии.

### Вариант 2: Внешний сервис (Unleash, LaunchDarkly, самописный на Redis)

* **Плюсы:** индустриальный стандарт, богатый UI, SDK для разных языков.
* **Минусы:** новые сервисы в инфраструктуре — усложняет Air-gapped поставку; дополнительная точка отказа; неоправданная сложность для LMS.

### Вариант 3: Глобальная таблица в PostgreSQL + in-memory кэш приложения (выбранный)

* **Плюсы:**
  * нулевые новые зависимости (PostgreSQL уже есть);
  * транзакционность и аудит через общий `audit_log`;
  * проверка флагов — O(1) в памяти;
  * LISTEN/NOTIFY для реактивного обновления кэша без Redis.
* **Минусы:**
  * требует выделенного LISTEN-соединения на каждый инстанс `api` (влияет на `max_connections`);
  * окно рассинхронизации кэшей между инстансами до 60 секунд (mitigation — периодическая синхронизация).

## Принятое решение

Выбран **Вариант 3: гибридная модель (Вариант B) — глобальная таблица + tenant overrides, PostgreSQL как source of truth, in-memory кэш приложения.**

### 1. Модель данных и источник истины

* **Источник истины:** PostgreSQL.
* **Глобальные флаги:** таблица `feature_flags` (вне RLS). Содержит `name`, `description`, `enabled` (значение по умолчанию), `is_delegatable` (может ли тенант-админ переключать), `created_at`, `updated_at`.
* **Тенантные переопределения (overrides):** таблица `tenant_feature_flags` (защищена RLS). Содержит `tenant_id`, `flag_name`, `enabled`, `updated_by`, `updated_at`.
* **Правило наследования (Вариант A):** если для `(tenant_id, flag_name)` нет записи в `tenant_feature_flags`, применяется значение `enabled` из глобальной таблицы `feature_flags`.

Детальная структура таблиц — в [`../FEATURE_FLAGS.md`](../FEATURE_FLAGS.md) и [`../DB_SCHEMA.md`](../DB_SCHEMA.md) §1.2.

### 2. Механизм кэширования и синхронизации

* **In-memory кэш:** каждый инстанс Axum хранит состояние флагов в памяти:
  * `global: HashMap<String, GlobalFlag>` — глобальные флаги;
  * `tenant_overrides: HashMap<(TenantId, String), bool>` — тенантные переопределения.
* **Инициализация:** при старте инстанса выполняется **синхронная загрузка** всех флагов из БД (до порога 100 000 тенантов).
* **Масштабируемость кэша:** при превышении порога 100 000 активных тенантов `tenant_overrides` заменяется на LRU-кэш (например, `moka`). При этом вводится флаг `cache_ready`:
  * пока `cache_ready = false` — проверка флага идёт **напрямую в БД** (медленнее, но безопасно);
  * после прогрева кэша — `cache_ready = true`, проверка идёт через кэш.
* **Реактивное обновление (Push):** PostgreSQL `LISTEN / NOTIFY`.
  * Создаётся **одно выделенное соединение** `sqlx::PgConnection` (owned, вне пула соединений).
  * Соединение выполняет `LISTEN` на каналы `feature_flags_changed` и `license_changed`.
  * Логика переподключения — с exponential backoff.
  * **Payload NOTIFY** содержит `flag_name` и опционально `tenant_id` (для override). Инстанс делает точечный `SELECT` по затронутым записям и обновляет только их в кэше — без полного сброса.
* **Периодическая синхронизация (Polling):** фоновая задача каждые **60 секунд** выполняет полное перечитывание состояния флагов из БД. Это страховка от потери NOTIFY при сетевых разрывах (PostgreSQL не хранит очередь NOTIFY).
* **Окно рассинхронизации** между инстансами — **до 60 секунд**. Это признано допустимым компромиссом для feature flags (не критично для бизнеса).

### 3. Разграничение доступа и API

* **Супер-администратор:** управляет глобальными флагами и создаёт тенантные переопределения через CLI (`rust-lms-cli features`) или внутренний API (`POST /api/v1/internal/features`).
* **Тенант-администратор:** может переключать флаги в своём `cpanel` **только если** для данного флага установлено `is_delegatable = true`. Для `is_delegatable = false` флаг отображается как «заблокировано администратором платформы».
* **Каскадная проверка в коде:**
  1. Проверка `license.features` (коммерческое право).
     * При отсутствии права — `403 Forbidden` + `{"error": "feature_not_licensed", "feature": "<name>"}`.
  2. Проверка `feature_flags` (операционное состояние).
     * При выключенном флаге — `403 Forbidden` + `{"error": "feature_not_enabled", "feature": "<name>"}`.
  3. При технической деградации (например, зависимый сервис недоступен) — `503 Service Unavailable`.

  Клиент различает три состояния по коду `error` в теле ответа.

## Последствия и риски

### Положительные

* Отсутствие новых внешних зависимостей — минимальный набор сервисов для Air-gapped.
* Транзакционность и единый источник истины в PostgreSQL.
* Изменения флагов автоматически попадают в общий `audit_log` платформы.
* Проверка флагов в горячем пути — O(1) в памяти (микросекунды).

### Отрицательные / Риски

* **Увеличение количества долгоживущих соединений к PostgreSQL** — на 1 LISTEN-соединение на каждый инстанс `api`. Формула для расчёта:
```
max_connections ≥ (N_api × (pool_size + 1)) + (N_workers × pool_size) + резерв 20%
```

Где `+1` — это LISTEN-соединение, а резерв нужен для миграций, административных сессий и мониторинга.
**Ограничение:** PgBouncer в режиме `transaction pooling` **не поддерживает LISTEN/NOTIFY**. Работа LISTEN через PgBouncer возможна только в `session pooling`, что снижает эффективность пула. Это нужно учитывать при масштабировании.
**При масштабировании > N инстансов** (значение N определяется нагрузочным тестированием) — вынос LISTEN в отдельный сервис-реле (требует нового ADR).

* **Пиковая нагрузка при массовом изменении флагов** (например, через админ-скрипт). Все инстансы одновременно начнут перечитывать состояние. **Митигация:** изменение флага через API обновляет кэш инстанса-инициатора сразу, остальные инстансы получают NOTIFY асинхронно и обновляют только затронутые записи (не всё состояние).

* **Окно рассинхронизации кэшей** между инстансами — **до 60 секунд** (при потере NOTIFY). Признано допустимым для feature flags. **Митигация:** периодическая синхронизация (60 сек) + точечный payload NOTIFY.

* **Риск отравления кэша** при ошибке парсинга payload NOTIFY или аномальном состоянии. **Митигация:**
* после любого обновления кэша — sanity check (количество флагов не изменилось внезапно; значения в допустимых пределах);
* при аномалии — fallback на полное перечитывание из БД;
* логирование инцидента в `audit_log` с `%reason = 'cache_poisoning_detected'`.
