# Тема: Application-Level Encryption: KMS, blind index, миграция

## Контекст и постановка проблемы

Платформа хранит персональные данные (PII) пользователей тенанта: email, ФИО, external_id, а также свободные атрибуты в `users.metadata`. Для части тенантов (госсектор, крупные корпорации, обработка ПДн граждан РФ) требований «шифрование на уровне СУБД (TDE) + TLS» недостаточно — нужна защита от компрометации учётной записи БД и от администратора БД.

Спецификация ALE зафиксирована в [`../STANDARDS.md`](../STANDARDS.md) §«Application-Level Encryption». Настоящий ADR фиксирует выбор KMS/Vault-схемы, формата детерминированного шифрования для поиска и процедуры миграции существующих тенантов.

## Драйверы решения (Decision Drivers)

* **Соответствие требованиям.** 152-ФЗ, GDPR, отраслевые стандарты для госсектора.
* **Поиск по зашифрованным полям.** Аутентификация по email и поиск по external_id должны работать без расшифровки всей таблицы.
* **Производительность.** Бюджеты по задержкам — в [`../NFR.md`](../NFR.md) §8.
* **Возможность отключения.** Тенант может не использовать ALE.
* **Air-gapped.** Решение должно работать в закрытом контуре без внешних KMS-сервисов.

## Рассмотренные варианты и трейд-оффы (Trade-offs)

### Вариант 1: Только шифрование на уровне СУБД (TDE)

* **Плюсы:** нулевая стоимость на стороне приложения, стандартная практика.
* **Минусы:** не защищает от администратора БД и от компрометации учётной записи. Не покрывает требования госсектора.

### Вариант 2: ALE с облачным KMS (AWS KMS / GCP KMS / Azure Key Vault)

* **Плюсы:** управляемая инфраструктура, высокая доступность, ротация ключей из коробки.
* **Минусы:** не работает в Air-gapped; vendor lock-in; трансграничная передача при использовании облачного KMS из другого региона.

### Вариант 3: ALE с self-hosted Vault (HashiCorp Vault)

* **Плюсы:**
  * работает в Air-gapped;
  * полный контроль над ключами;
  * единый сервис для KEK и release-ключа плагинов (см. ADR-0003).
* **Минусы:** дополнительный сервис в инфраструктуре; требуется администрирование.

## Принятое решение

Выбран **Вариант 3: ALE с self-hosted HashiCorp Vault** (или совместимый KMS с аналогичным API).

1. **Схема шифрования:** envelope encryption.
   * **DEK (Data Encryption Key)** — уникальный для тенанта, шифрует PII-поля (AES-256-GCM).
   * **KEK (Key Encryption Key)** — шифрует DEK, хранится в Vault.
2. **Область применения (по умолчанию):** `users.email`, `users.first_name`, `users.last_name`, `users.external_id`, PII-поля внутри `users.metadata` (декларативно через схему ETL).
3. **Область применения (опционально, по требованию тенанта):** `chat_messages.content`, `assignments.instruction_text`.
4. **Поиск по зашифрованным полям:**
   * `email` — **детерминированное шифрование** AES-SIV (одинаковый plaintext → одинаковый ciphertext в рамках тенанта). Это позволяет индексировать поле и искать по точному значению (аутентификация по email).
   * `external_id` — то же (AES-SIV).
   * `first_name` / `last_name` — обычное AES-GCM (без поиска).
5. **Ротация:**
   * DEK — по расписанию, по умолчанию раз в год; конфигурируется тенантом.
   * KEK — по регламенту инфраструктуры (Vault).
   * Ротация выполняется онлайн, без остановки сервиса.
6. **Опциональность:** ALE — опция на уровне тенанта. Включение требует явного решения администратора тенанта. Отключение не удаляет уже зашифрованные данные — требуется отдельная миграция.
7. **Стоимость:** ALE добавляет ≤ 5 мс к p95 чтения/записи пользовательских полей; поиск по email через blind index — ≤ 10 мс к p95 (см. [`../NFR.md`](../NFR.md) §8).

## Последствия и риски

* **Безопасность:** компрометация учётной записи PostgreSQL не даёт доступа к PII — нужен ещё Vault и KEK.
* **Производительность:** см. бюджеты выше; при превышении — оптимизация через кэширование DEK в памяти на короткое время.
* **Эксплуатация:** требуется Vault в инфраструктуре (уже добавлен для release-ключа плагинов — см. [`../DEPLOY.md`](../DEPLOY.md) §3).
* **Миграция:** для существующего тенанта с включённым ALE — фоновая миграция (шифрование существующих записей). Регламент миграции — часть этого ADR (см. ниже).
* **Риски и митигация:**
  * **Риск:** потеря KEK = потеря данных. **Митигация:** бэкап KEK в Vault; при Air-gapped — бэкап в локальном хранилище заказчика с ограниченным доступом.
  * **Риск:** AES-SIV детерминированное шифрование позволяет атакующему с доступом к БД определить, что два пользователя имеют одинаковый email. **Митигация:** это допустимый трейд-офф для поиска по email; альтернатива — blind index (HMAC) — рассматривается как второй вариант в реализации.
  * **Риск:** миграция на ALE создаёт окно, когда часть данных зашифрована, часть — нет. **Митигация:** миграция выполняется по схеме «dual-read» (при чтении понимаем оба формата) до полного завершения.
