# Спецификация Offline-First PWA и Управления Синхронизацией

**Файл спецификации:** `specs/OFFLINE_SYNC.md`

> Смежные разделы: NFR и лимиты — в `NFR.md` §4; схема БД — в `DB_SCHEMA.md`; API синхронизации — в `OPEN_API.md` §3.4; структура крейта client — в `STRUCTURE.md` §3.5.

## 1. Регламент Офлайн-функциональности

### 1.1. Границы применимости
Платформа функционирует как Progressive Web App (PWA) с использованием Service Workers, обеспечивая непрерывность обучения без сети.

**Офлайн работает только в клиентском WASM-контуре Leptos.** SSR-страницы (публичный сайт, лендинги, страница верификации сертификата) не кэшируются для офлайна. Service Worker кэширует только оболочку приложения (app shell).

### 1.2. Переключение маршрутизации
При отсутствии сети Service Worker перехватывает запросы к защищенным маршрутам и перенаправляет их на офлайн-оболочку с соответствующим UI-индикатором. Пользователь видит, что работает в офлайн-режиме, и может продолжать обучение.

### 1.3. Ограничения платформ

| Платформа | Уровень поддержки офлайна | Комментарий |
|:---|:---|:---|
| **Desktop (Chrome/Firefox/Edge)** | Полный | IndexedDB без ограничений, Background Sync работает. |
| **Android (Chrome)** | Полный | IndexedDB работает стабильно, Background Sync поддерживается. |
| **iOS (Safari)** | Ограниченный | IndexedDB может быть очищена после **7 дней бездействия**, отсутствие Background Sync, ограниченный WASM-кэш. |

**Для iOS-сегмента** целевой сценарий полного офлайна закрывается **нативным мобильным приложением** (приоритетное направление в `ROADMAP.md` §«Мобильное приложение»). До его выхода iOS-пользователи получают ограниченный офлайн: текст, тесты, WASM-модули в пределах лимитов `NFR.md`; медиа — только онлайн.

### 1.4. Офлайн-шелл формы входа
Статические ассеты формы входа кэшируются Service Worker. Логика проверки сессии и SSO-валидации требует сети (реализуется на бэкенде).

### 1.5. Допустимые операции в офлайне
- **Студент:** просмотр структуры курса, прохождение текстовых материалов, прохождение локальных тестов, генерация xAPI-стейтментов (запись в IndexedDB).
- **Администратор:** просмотр dashboard, управление feature flags (для делегированных), генерация административных xAPI-стейтментов.
- **Запрещено:** создание новых пользователей, импорт SCORM, изменение настроек тенанта — эти операции требуют онлайна.

## 2. Структура Клиентского Хранилища (IndexedDB)

Используется **IndexedDB** через `web-sys` API. Реализация — в `crates/client/src/shared/storage.rs`.

### 2.1. Object Store: `offline_xapi_statements`

Хранит xAPI-стейтменты, сгенерированные в офлайне и ожидающие синхронизации.

| Поле | Тип | Описание |
|:---|:---|:---|
| `id` | UUID v4 | Первичный ключ (`keyPath`). |
| `timestamp` | ISO 8601 | Время события с учетом NTP-дельты. Индекс для сортировки. |
| `actor` | JSON | Идентификатор пользователя. |
| `verb` | JSON | IRI глагола (например, `completed`, `answered`). |
| `object` | JSON | Целевой объект (курс, тест, юнит). |
| `queue_name` | String | `"student"` или `"admin"` — для фильтрации при синхронизации. |
| `retry_count` | Integer | Счетчик попыток синхронизации (0 по умолчанию). |
| `stored_at` | TIMESTAMPTZ | Null до успешной синхронизации; устанавливается сервером. |

**Индексы:**
- `timestamp` — для сортировки при чанковом чтении.

### 2.2. Object Store: `client_clock`

Хранит результат калибровки времени устройства относительно серверного NTP.

| Поле | Тип | Описание |
|:---|:---|:---|
| `id` | String | `"current"` (единственная запись). |
| `delta_ms` | Integer | Смещение в миллисекундах: `server_time - client_time`. |
| `updated_at` | ISO 8601 | Время последней калибровки. |

### 2.3. Формат xAPI Statement (JSON-LD)

Все стейтменты следуют спецификации xAPI (IEEE 1730):

```json
{
  "id": "uuid-v4",
  "timestamp": "2026-10-02T14:30:00Z",
  "actor": {
    "objectType": "Agent",
    "account": {
      "homePage": "https://tenant.lms.example",
      "name": "user_123"
    }
  },
  "verb": {
    "id": "http://adlnet.gov/expapi/verbs/completed",
    "display": { "en": "completed" }
  },
  "object": {
    "objectType": "Activity",
    "id": "https://tenant.lms.example/courses/uuid/units/uuid"
  },
  "stored_at": null,
  "queue_name": "student",
  "retry_count": 0
}
```

## 3. Политики Кэширования Медиа-контента

### 3.1. On-Demand Caching
Кэширование тяжелых медиафайлов (видео/аудио) не является принудительным и гибко управляется настройками:

- **На уровне платформы:** Администратор тенанта может ограничить офлайн-скачивание видео (флаг `allow_offline = false`). Медиа отдаётся только по подписанным URL с коротким TTL, опционально — DRM (Widevine/FairPlay/PlayReady).
- **На уровне пользователя:** Студент сам решает, скачивать ли медиаматериалы юнита для изучения в офлайне (с выбором качества), или обучаться без сети только с использованием текста, тестов и легковесных WASM-модулей.

### 3.2. Лимиты
- Размер offline-очереди IndexedDB на устройство: **≤ 200 МБ** (см. `NFR.md` §4).
- Количество statements в offline-очереди: **≤ 50 000**.
- Размер одного медиафайла в DAM: **≤ 5 ГБ**.

## 4. Алгоритм Транзакционной Синхронизации

При восстановлении сети (`online` event) запускается процесс синхронизации. Реализация — в `crates/client/src/student/services/offline_queue.rs` и `crates/client/src/admin/services/offline_queue.rs`.

### 4.1. Пошаговый процесс

1. **Проверка SSO:** Перед синхронизацией проверяется валидность сессии. Если сессия истекла — синхронизация откладывается до повторного входа.

2. **Калибровка времени (Clock Sync):**
   - Клиент запрашивает серверное время через NTP-эндпоинт (в текущей реализации — `mock` с фиксированной дельтой).
   - Вычисляется `delta_ms = server_time - client_time`.
   - Все `timestamp` в стейтментах корректируются на `delta_ms`.
   - **Fallback:** если NTP недоступен, `delta_ms = 0` с логированием warning.

3. **Chunked Reading:**
   - Чтение записей из IndexedDB чанками по **50 штук**.
   - Сортировка по индексу `timestamp` (от старых к новым).
   - Фильтрация по `queue_name` ("student" или "admin").

4. **Bulk Upload:**
   - Отправка чанка на бэкенд через `POST /api/v1/analytics/lrs/sync` (см. `OPEN_API.md` §3.4).
   - В текущей реализации используется `mock_sync_api` с задержкой 800 мс для тестирования UI.

5. **Two-Phase Commit:**
   - Если сервер ответил `200 OK` с массивом `accepted` (список успешно сохраненных ID):
     - Атомарное удаление этих записей из IndexedDB через `delete_statements`.
     - Логирование: `[StudentQueue] Deleted N statements from DB`.
   - Если сервер ответил ошибкой или сеть недоступна:
     - Инкремент `retry_count` для каждой записи в чанке.
     - Если `retry_count` превысил лимит — запись удаляется с логированием error.
     - Синхронизация прерывается (`break`), повторная попытка — при следующем `online` event.

6. **Обновление UI:**
   - Глобальный сигнал `queue_size_signal` обновляется с количеством оставшихся записей.
   - UI отображает индикатор синхронизации (спиннер, прогресс-бар).

### 4.2. Политики Retry

| Контур | Максимум попыток | Обоснование |
|:---|:---:|:---|
| **Student** | 3 | Студенческие данные менее критичны; при превышении — удаление с логом. |
| **Admin** | 10 | Административные действия (например, создание batches) более важны; больше попыток для надежности. |

**При превышении лимита:**
- Запись удаляется из IndexedDB.
- В консоль выводится error: `[StudentQueue] Statement {id} exceeded max retries, discarding`.
- Событие теряется (осознанный компромисс: лучше потерять 1 из 1000 стейтментов, чем заблокировать очередь навсегда).

### 4.3. Иммутабельность исторических фактов

Клиент **не модифицирует** записи в IndexedDB после их создания. Единственное изменение — инкремент `retry_count` при ошибке синхронизации. Это соответствует принципу append-only в LRS (см. ADR `2026.09.28-0002.md`).

### 4.4. Разрешение конфликтов (Сохранение всех попыток)

При восстановлении сети менеджер синхронизации транзакционно передает данные на бэкенд по принципу **At-least-once**. Если студент выполнял задания на разных офлайн-устройствах, система гарантированно сохраняет обе попытки в историю LRS, фиксируя точные временные метки их реального прохождения. Хронология цифрового следа не перезаписывается, а финальная оценка рассчитывается на основе политик курса (см. `STANDARDS.md` §«Calculations Engine»).

## 5. Регламент Разрешения Конфликтов

### 5.1. Клиентская калибровка времени (NTP-дельта)

Клиент калибрует свое время относительно сервера:
- При первом запуске и периодически (раз в час) запрашивает серверное время.
- Вычисляет `delta_ms` и сохраняет в `client_clock`.
- Все генерируемые стейтменты получают `timestamp = client_time + delta_ms`.

### 5.2. Fallback на `delta_ms = 0`

Если NTP-эндпоинт недоступен (сеть отсутствует, сервер не отвечает):
- `delta_ms = 0`.
- В консоль выводится warning: `[ClockSync] NTP unavailable, using client time`.
- Стейтменты пишутся с клиентским временем.

### 5.3. Сброс дельты при смене пользователя

При logout или смене пользователя:
- `client_clock` очищается.
- При следующем login — повторная калибровка.

### 5.4. Calculations Engine (пост-процессинг)

Серверная логика (не входит в зону ответственности клиента):
- При получении стейтментов через `POST /api/v1/analytics/lrs/sync` сервер проверяет их на дубликаты (по `id`).
- Если дубликат найден — отклоняется с `rejected` в ответе.
- Уникальные стейтменты сохраняются в LRS (TimescaleDB или ClickHouse).
- Асинхронный Calculations Engine пересчитывает прогресс, оценки, сертификаты на основе новых данных.

## 6. Архитектурные достижения

1. **Изоляция контуров:** `student` и `admin` имеют независимые очереди с разными политиками retry (3 vs 10) и приоритетами.
2. **Типобезопасная реактивность:** Глобальные сигналы `AppQueueState` через `provide_context`/`use_context` без коллизий типов.
3. **Защита от утечек памяти:** Слушатели `online`/`offline` привязаны к `App` (никогда не размонтируется), а не к страницам.
4. **SSR-безопасность:** Все вызовы `web_sys` защищены `#[cfg(target_arch = "wasm32")]`, серверные заглушки (no-op) для нативной сборки.
5. **DRY-ядро:** `QueueCore<T>` — обобщенная основа, специализируемая под конкретные контуры через `StudentQueue`/`AdminQueue`.
6. **PWA-инфраструктура:** Service Worker + Manifest + оффлайн-индикаторы в UI.

## 8. Ограничения и что НЕ входит в скоуп WASM-клиента

Следующие требования спецификации реализуются на стороне бэкенда и не входят в зону ответственности клиентского крейта:

- **LRS (Learning Record Server)** на Axum — прием xAPI statements.
- **Signed URLs** для DAM-хранилища (HMAC-SHA256).
- **DRM-интеграция** (Widevine/FairPlay) для Enterprise-тенантов.
- **Calculations Engine** — асинхронный пост-процессинг успеваемости.
- **SSO-интеграция** (OIDC/SAML2/LDAP) для проверки сессии.
- **NTP-эндпоинт** для реальной калибровки времени.
