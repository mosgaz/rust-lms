# Подсистема лицензирования (On-Premise / Air-gapped)

**Файл спецификации:** `LICENSING.md`

> Смежные разделы: общие NFR и SLA — в [`NFR.md`](NFR.md); Air-gapped поставка — в [`DEPLOY.md`](DEPLOY.md) §4; Disaster Recovery — в [`DEPLOY.md`](DEPLOY.md) §4.3; формат ADR — в [`decisions/README.md`](decisions/README.md); ADR по этой теме — [`decisions/2026.09.29-0008.md`](decisions/2026.09.29-0008.md).

## 1. Назначение и область применения

Для коробочных поставок (On-Premise и Air-gapped) платформа ограничивает функционал и масштаб в соответствии с лицензионным ключом, выданным вендором. Это стандартная практика для коммерческих коробочных продуктов (Atlassian, GitLab, JetBrains, Docebo, Cornerstone).

Подсистема лицензирования **не затрагивает SaaS-поставку**: там лимиты и биллинг управляются на уровне платформы и не требуют офлайн-валидации.

Ключевые требования:

* **Офлайн-валидация.** Никаких внешних вызовов для проверки лицензии. В Air-gapped внешние вызовы физически невозможны.
* **Криптографическая стойкость.** Лицензионный ключ не может быть подделан или отредактирован без знания приватного ключа вендора.
* **Прозрачность.** Администратор заказчика в любой момент видит: срок действия, лимиты, текущее потребление.
* **Мягкая деградация.** При истечении лицензии платформа не «отключается моментально» — есть grace period.
* **Ротация.** При смене hardware (переезд на новый сервер) лицензия перевыпускается без потери данных.

## 2. Формат лицензионного ключа

Лицензионный ключ — **JWT-подобный токен**, подписанный release-ключом вендора (Ed25519, тот же алгоритм, что и `.wasm.sig` плагинов — см. [`PLUGIN.md`](PLUGIN.md) §7.1). Формат: `<base64url(header)>.<base64url(payload)>.<base64url(signature)>`.

### Header

```json
{
  "alg": "Ed25519",
  "typ": "RUST-LMS-LICENSE",
  "kid": "vendor-key-2026-09"
}
```

### Payload

```json
{
  "license_id": "uuid-v4",
  "customer_name": "ООО «Пример»",
  "issued_at": "2026-09-29T00:00:00Z",
  "expires_at": "2027-09-29T00:00:00Z",
  "grace_period_days": 30,
  "binding": {
    "type": "node_locked",
    "hardware_id": "sha256:abcdef...",
    "allowed_drift": ["same_hardware", "reissue_on_change"]
  },
  "limits": {
    "max_tenants": 5,
    "max_users": 1000,
    "max_plugins": 500,
    "max_admins": 10
  },
  "features": {
    "ale": true,
    "scim": true,
    "drm": false,
    "scorm_2004_sequencing": false
  },
  "support_level": "enterprise",
  "issued_by": "vendor@example.com"
}
```

### Подпись

Ed25519-подпись над `base64url(header) + "." + base64url(payload)`. Публичный ключ верификации вшивается в бинарник платформы на этапе сборки (по аналогии с публичным ключом `.wasm.sig`).

## 3. Типы привязки (binding)

| Тип | Описание | Когда используется |
|:---|:---|:---|
| **`node_locked`** | Привязка к hardware ID (SHA-256 от CPU ID + MAC-адрес primary NIC + серийный номер диска). | Air-gapped, одиночный сервер. Рекомендуется по умолчанию. |
| **`domain_locked`** | Привязка к внутреннему домену заказчика (FQDN из `sso_config`). | On-Premise с несколькими узлами, единый домен. |
| **`floating`** | Без привязки к hardware; валидна на любом узле, но с ограничением одновременных инстансов (max_nodes). | Enterprise с кластером, где hardware может меняться (например, автоскейл). Требует дополнительной проверки через heartbeat внутри кластера. |

## 4. Валидация

Валидация выполняется **локально**, без внешних вызовов.

### Алгоритм

1. При старте `rust-lms-api-server` читает лицензионный ключ из:
   * переменной окружения `RUST_LMS_LICENSE_KEY` (для SaaS/CI);
   * файла `/etc/rust-lms/license.key` (для On-Premise);
   * таблицы `license` в БД (для повторного чтения).
2. Проверяет подпись через публичный ключ вендора (Ed25519).
3. Проверяет срок действия (`expires_at` + `grace_period_days`).
4. Проверяет привязку:
   * `node_locked` — сравнивает текущий hardware ID с `hardware_id` из payload;
   * `domain_locked` — сравнивает FQDN;
   * `floating` — проверяет количество активных инстансов через внутренний heartbeat (не внешний).
5. Записывает результат в таблицу `license` (см. §6).
6. Логирует статус в `audit_log`.

### Ошибки валидации

| Ошибка | Поведение |
|:---|:---|
| **Неверная подпись** | Платформа не стартует. Логируется `LICENSE_SIGNATURE_INVALID`. |
| **Срок истёк, grace period активен** | Платформа работает в режиме «предупреждение»: в UI администратора — баннер; в `audit_log` — ежедневная запись. Новые тенанты/пользователи сверх лимитов не создаются. |
| **Срок истёк, grace period завершён** | Платформа работает в режиме «ограничение»: read-only для новых операций (создание тенантов, пользователей, плагинов), но существующие данные доступны. См. §5. |
| **Hardware ID не совпадает** | Платформа не стартует. Логируется `LICENSE_HARDWARE_MISMATCH`. Требуется перевыпуск ключа у вендора. |
| **Лимит превышен** | Платформа работает, но операции, превышающие лимит, отклоняются с `403 License limit exceeded`. |

## 5. Enforcement: soft vs hard

Платформа различает **soft** (предупреждение) и **hard** (ограничение) enforcement. Выбор зависит от состояния лицензии.

### Soft enforcement (по умолчанию)

* Действует в пределах срока и grace period.
* Ограничения применяются только к **превышению лимитов** (создание сверх `max_tenants` / `max_users` / `max_plugins` / `max_admins`).
* Отключение **features** (например, `ale: false`) приводит к тому, что эндпоинты/функции возвращают `403 Feature not licensed`.
* В UI администратора — баннер со статусом лицензии и текущим потреблением.

### Hard enforcement

* Действует после истечения grace period.
* Платформа переходит в режим **ограничения**: разрешены только чтение и экспорт данных; операции создания/изменения отклоняются с `403 License expired`.
* **Данные не удаляются.** Администратор заказчика может выгрузить всё содержимое через существующие эндпоинты экспорта (см. [`STANDARDS.md`](STANDARDS.md) §«Соответствие GDPR / CCPA»).
* После установки новой лицензии платформа автоматически возвращается в нормальный режим без перезапуска (перечитывает файл / таблицу).

### Что не блокируется никогда

* Аутентификация (вход).
* Чтение существующих данных.
* Экспорт данных.
* Работа фоновых воркеров по уже начатым задачам.
* Сбор xAPI (LRS продолжает принимать statements).

Это осознанный выбор: даже при истёкшей лицензии заказчик должен иметь доступ к своим данным.

## 6. Таблица `license` в БД

Лицензия хранится в глобальной таблице `license` (вне RLS — это инфраструктурный уровень, не тенант).

* `id`: UUID (Primary Key).
* `license_id`: VARCHAR(64) (UNIQUE). Идентификатор из payload.
* `customer_name`: VARCHAR(255).
* `issued_at` / `expires_at`: TIMESTAMPTZ.
* `grace_period_days`: INTEGER.
* `binding_type`: VARCHAR(32) (CHECK: `'node_locked'`, `'domain_locked'`, `'floating'`).
* `hardware_id`: VARCHAR(128) (NULLable).
* `domain_fqdn`: VARCHAR(255) (NULLable).
* `limits`: JSONB.
* `features`: JSONB.
* `raw_payload`: JSONB (полный payload для аудита).
* `signature_verified`: BOOLEAN (результат проверки подписи).
* `last_validated_at`: TIMESTAMPTZ.
* `status`: VARCHAR(32) (CHECK: `'active'`, `'grace'`, `'expired'`, `'hard_limited'`, `'invalid'`).
* `created_at` / `updated_at`: TIMESTAMPTZ.

Таблица `license` — единственная запись (single-row). При ротации ключа старая запись архивируется в `audit_log`, новая записывается поверх.

## 7. API для административной панели

### `GET /api/v1/internal/license`

* **Уровень доступа:** Глобальный токен супер-администратора (`infrastructure:monitor`) или локальный токен администратора тенанта с правами `license:read` (см. [`RBAC.md`](RBAC.md)).
* **Назначение:** Просмотр текущего состояния лицензии.
* **Ответ:**
  ```json
  {
    "license_id": "uuid-v4",
    "customer_name": "ООО «Пример»",
    "status": "active",
    "expires_at": "2027-09-29T00:00:00Z",
    "grace_period_days": 30,
    "limits": { "max_tenants": 5, "max_users": 1000, "max_plugins": 500, "max_admins": 10 },
    "current_usage": { "tenants": 3, "users": 720, "plugins": 120, "admins": 4 },
    "features": { "ale": true, "scim": true, "drm": false },
    "binding": { "type": "node_locked", "hardware_id_match": true }
  }
  ```

### `POST /api/v1/internal/license` (только On-Premise)

* **Уровень доступа:** Глобальный токен супер-администратора (`infrastructure:provisioning`).
* **Назначение:** Установка новой лицензии (например, после продления или ротации).
* **Входящий Payload:** `{ "license_key": "<...>" }`.
* **Поведение:** Подпись проверяется, ключ записывается в файл и в таблицу `license`, платформа перечитывает статус без перезапуска.
* **Ответ:** `200 OK` с обновлённым статусом (формат тот же, что у `GET`).

> В Air-gapped эндпоинт может быть недоступен (внешний API отключён). Установка лицензии выполняется через CLI `rust-lms-license` (см. §8).

## 8. CLI `rust-lms-license`

Утилита командной строки для работы с лицензией в Air-gapped.

* `rust-lms-license install --file /path/to/license.key` — установка лицензии.
* `rust-lms-license status` — вывод текущего статуса.
* `rust-lms-license hardware-id` — вывод hardware ID текущего сервера (для передачи вендору при выпуске лицензии).
* `rust-lms-license validate --file /path/to/license.key` — проверка ключа без установки.

CLI входит в дистрибутив (см. [`DEPLOY.md`](DEPLOY.md) §4.1) и работает локально, без внешних вызовов.

## 9. Ротация ключа при смене hardware

При переезде на новый сервер (или замене hardware) администратор заказчика:

1. Запускает `rust-lms-license hardware-id` на новом сервере — получает новый hardware ID.
2. Передаёт новый hardware ID вендору через согласованный канал (защищённая почта / портал).
3. Вендор выпускает новый лицензионный ключ с тем же `license_id`, но новым `hardware_id`.
4. Администратор устанавливает ключ через `rust-lms-license install`.

Пока ключ не установлен — платформа на новом сервере не стартует (`LICENSE_HARDWARE_MISMATCH`). Данные не теряются: они уже перенесены вместе с бэкапом (см. [`DEPLOY.md`](DEPLOY.md) §4.3).

## 10. Grace period

* **По умолчанию:** 30 дней. Конфигурируется вендором при выпуске ключа (payload `grace_period_days`).
* **Поведение:** в grace period платформа работает в soft enforcement, но в UI администратора — заметный баннер «Лицензия истекла, N дней до ограничения».
* **Уведомления:** в `audit_log` — ежедневная запись; в вебхуках — событие `license.grace_started` (см. [`OPEN_API.md`](OPEN_API.md) §4.1, при следующей правке).
* **После grace period:** hard enforcement (см. §5).

## 11. Ограничения и что НЕ входит в скоуп

* **SaaS-поставка** — не использует офлайн-лицензию; лимиты и биллинг управляются на уровне платформы.
* **Trial-режим** — отдельно не выделяется; trial — это обычная лицензия с коротким `expires_at` (например, 14 дней).
* **Автоматический онлайн-ре-активейшн** — не реализуется; всё офлайн.
* **Привязка к MAC-адресу** — только как часть hardware ID, не единственный идентификатор (MAC может меняться).
* **Привязка к IP** — не используется (в Air-gapped IP может меняться).
* **Подсчёт активных пользователей по сессиям** — только по количеству записей в `users`, без учёта сессий (иначе лимит будет «плавать» и вызывать ложные блокировки).

## 12. Связь с ADR

Формат лицензионного ключа, тип привязки и политика enforcement — архитектурное решение. ADR: [`2026.09.29-0008.md`](decisions/2026.09.29-0008.md) (статус: Предложено).

ADR фиксирует:

* алгоритм подписи (Ed25519) и формат ключа (JWT-подобный);
* три типа binding (`node_locked`, `domain_locked`, `floating`);
* политику soft / hard enforcement;
* grace period и его поведение;
* схему таблицы `license` и эндпоинты API.
