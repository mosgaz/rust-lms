## AGENTS.md — Инструкции для AI-агентов
Этот файл — первичная точка входа для любого AI-агента (Claude Code, Cursor, Cline, Codex, Copilot), работающего с репозиторием lms-core.
## 🚦 Перед выполнением ЛЮБОЙ задачи
Выполняй эти шаги строго по порядку:

   1. Прочитай SPECIFICATION.md — это главный источник истины для бизнес-требований. Пойми концепцию, в каком крейте ты работаешь и какие у него архитектурные границы.
   2. Прочитай STRUCTURE.md — пойми физическую структуру каталогов проекта, распределение файлов по слоям и правила направленности зависимостей.
   3. Прочитай технические спецификации, относящиеся к твоей задаче:
   * Если меняешь структуру БД или логику аналитики LRS — изучи DB_SCHEMA.md.
      * Если разрабатываешь или правишь эндпоинты, токены и вебхуки — изучи OPEN_API.md.
      * Если работаешь над PWA, Service Worker или очередями IndexedDB — изучи OFFLINE_SYNC.md.
      * Если вносишь изменения в рантайм плагинов или SDK — изучи PLUGIN.md и шаблон PLUGIN_DEVELOPMENT_TEMPLATE.md.
      * Если правишь конфигурацию контейнеров, сетевые шлюзы или CSP — изучи DEPLOY.md.
   4. Прочитай CODING_STANDARDS.md — следуй правилам full-stack Rust буквально. Это закон, а не рекомендация.
   5. Определи ответственность — если задача выходит за рамки текущего крейта или нарушает изоляцию тенантов, остановись и спроси.
   6. Проверь dependency rules (§4 STRUCTURE.md) — твой код не должен нарушать направления зависимостей (например, общие типы данных lms-shared-types не могут импортировать логику из lms-core-backend).
   7. Напиши тесты — для любой новой публичной функции, эндпоинта Open API или контракта SDK. Без тестов задача не считается выполненной.
   8. Запусти локальные проверки перед коммитом:
   
   cargo clippy --all-targets --all-features -- -D warnings
   cargo fmt --all -- --check
   cargo test --workspace

## 📦 Структура крейтов
Проект представляет собой Cargo workspace из micro-crates (каждый ≤ 1500 строк кода):

crates/
├── lms-core-backend/    # Бэкенд-ядро на Rust (Axum / Actix-web, маршрутизация, Open API)
├── lms-core-frontend/   # Изоморфный фронтенд на Rust Leptos (PWA, SSR + Hydration)
├── lms-shared-types/    # Общие структуры данных, DTO, схемы xAPI Statements (Zero-Copy)
├── lms-database-db/     # Слой работы с PostgreSQL, миграции, логика сессий RLS
├── lms-lrs-analytics/   # Движок LRS хранилища (инвариантный слой TimescaleDB / ClickHouse)
├── lms-plugin-sdk/      # SDK для микроприложений (WASM-биндинги и postMessage мосты)
├── lms-etl-mapper/      # Конвейер кастомного импорта/экспорта пользователей (CSV/XLSX ETL)
└── lms-task-worker/     # Асинхронные воркеры фоновых задач (In-Memory Tokio / River)

## 🎯 Критерии выполненной задачи
Задача считается выполненной, если:

* Код компилируется без warnings (cargo clippy -- -D warnings).
* Форматирование соответствует стандарту (cargo fmt --check).
* Все новые публичные функции и эндпоинты покрыты тестами (≥ 80% покрытия для ETL и LRS-парсеров).
* Нет unwrap() / expect() в runtime-коде (особенно в WASM фронтенда, паника = краш PWA).
* Нет unsafe без комментария // SAFETY:.
* Каждый SQL-запрос к таблицам тенантов учитывает сессионный контекст tenant_id и правила RLS (см. DB_SCHEMA.md).
* Размер клиентского WASM-бандла не вырос более чем на 5% без архитектурного обоснования.
* Документация (doc-комментарии ///) написана для всех публичных API и контрактов Open API.

## 🚫 Что НЕЛЬЗЯ делать без согласования

   1. Добавлять новую зависимость в Cargo.toml — сначала обоснуй размер, влияние на компиляцию WASM и альтернативы на Rust.
   2. Использовать unsafe — в рамках LMS-логики он практически не нужен. Только с // SAFETY: и ревью.
   3. Менять публичные контракты данных в lms-shared-types — это ломает синхронизацию между бэкендом и WASM-клиентом.
   4. Нарушать изоляцию контента — запрещено добавлять сквозной шеринг данных между разными tenant_id (см. DB_SCHEMA.md).
   5. Писать синхронный блокирующий код в асинхронных пулах Tokio.
   6. Использовать println! — только структурированное логирование через tracing::*.

## 🆘 Если задача неясна
СПРОСИ. Не импровизируй.
Особенно уточняй:

* Касается ли задача логики конкретного тенанта или глобальной инфраструктуры (см. OPEN_API.md).
* Формат данных и xAPI глаголы (какие URI использовать для маппинга событий плагина; см. PLUGIN.md).
* Обработку ошибок (какой тип бизнес-ошибки вернуть через Open API).
* Поведение в офлайне (должна ли эта операция поддерживаться в IndexedDB-очереди PWA; см. OFFLINE_SYNC.md).

## 📊 Метрики качества

* Размер крейта: ≤ 1500 строк бизнес-логики (без учета тестов; см. STRUCTURE.md).
* Покрытие тестами: ≥ 80% для слоев lms-lrs-analytics, lms-etl-mapper, lms-plugin-sdk.
* Время CI: ≤ 10 минут на полную сборку и прогон верификации.
* WASM PWA бандл: ≤ 2.0 MB gzip (включая рантайм Leptos и базовые верифицированные плагины; см. DEPLOY.md).

## 🌐 Специфика стека

* Rust stable (последний стабильный релиз, никакой nightly-специфики).
* Leptos 0.7+ для изоморфного UI (единственный крейт, имеющий прямой доступ к DOM и Service Workers).
* Tailwind CSS для стилизации компонентов.
* IndexedDB через web-sys / gloo для обеспечения Offline-First очереди логов (см. OFFLINE_SYNC.md).
* Управление сессиями PostgreSQL RLS через установку локальных параметров сессии (см. DB_SCHEMA.md).
