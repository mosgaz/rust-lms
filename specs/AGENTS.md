# AGENTS.md — Инструкции для AI-агентов

Этот файл — **первичная точка входа** для любого AI-агента (Claude Code, Cursor, Cline, Codex, Copilot), работающего с репозиторием `lms-core`.

## 🚦 Перед выполнением ЛЮБОЙ задачи

Выполняй эти шаги **строго по порядку**:

1. **Прочитай `specs/SPECIFICATION.md`** — это главный источник истины для бизнес-требований.
2. **Прочитай `specs/STRUCTURE.md`** — пойми физическую структуру каталогов проекта, правила направленности зависимостей и Cargo workspace.
3. **Прочитай стандарты коммитов и ветвления `/CONTRIBUTING.md`**, Мы строго придерживаемся спецификации Conventional Commits для автоматической генерации семантического версионирования и формирования `CHANGELOG.md`. Каждый коммит должен соответствовать шаблону: `категория(область): описание`.
4. **Прочитай технические спецификации**, относящиеся к твоей задаче:
   * Если меняешь структуру БД или логику аналитики LRS — изучи [`specs/DB_SCHEMA.md`](DB_SCHEMA.md).
   * Если разрабатываешь или правишь эндпоинты, токены и вебхуки — изучи [`specs/OPEN_API.md`](OPEN_API.md).
   * Если работаешь над PWA, Service Worker или очередями IndexedDB — изучи [`specs/OFFLINE_SYNC.md`](OFFLINE_SYNC.md).
   * Если вносишь изменения в рантайм плагинов или SDK — изучи [`specs/PLUGIN.md`](PLUGIN.md) и шаблон [`specs/PLUGIN_DEVELOPMENT_TEMPLATE.md`](PLUGIN_DEVELOPMENT_TEMPLATE.md).
   * Если правишь конфигурацию контейнеров, сетевые шлюзы или CSP — изучи [`specs/DEPLOY.md`](DEPLOY.md).
   * Если задача затрагивает роли, доступы или логирование — изучи [`specs/RBAC.md`](RBAC.md) и [`specs/DIAGNOSTICS.md`](DIAGNOSTICS.md).
5. **Прочитай `specs/CODING_STANDARDS.md`** — следуй правилам full-stack Rust буквально. Это закон, а не рекомендация.
6. **Определи ответственность** — если задача выходит за рамки текущего крейта или нарушает изоляцию тенантов, остановись и спроси.
7. **Проверь dependency rules (§4 specs/STRUCTURE.md)** — твой код не должен нарушать направления зависимостей.
8. **Напиши тесты** — для любой новой публичной функции, эндпоинта Open API или контракта SDK. Без тестов задача не считается выполненной.
9. **Запусти локальные проверки** перед коммитом:
   ```bash
   cargo clippy --all-targets --all-features -- -D warnings
   cargo fmt --all -- --check
   cargo test --workspace
   ```

## 📦 Структура крейтов
Проект представляет собой Cargo workspace из **micro-crates** (каждый ≤ 1500 строк кода):
```text
crates/
├── shared/                   # Слой сетевых контрактов, структур сущностей и DTO
├── ui/                       # Общая библиотека Leptos UI компонентов и Tailwind CSS
├── api/                      # Ядро бизнес-логики, СУБД PostgreSQL (RLS) и LRS (без Leptos)
├── client/                   # Изоморфный Full-Stack веб-интерфейс, PWA и #[server] функции
└── server/                   # Сервер выполнения на Axum (Точка входа, Main)
```

## 🧠 1. Алгоритм мышления (Think Before Coding)
*   **Запрет на бесконечную диагностику:** Не зацикливайся на одном месте или циклическом исправлении одной и той же ошибки линтера. Если повторяешь одно и то же действие дважды — остановись и задай вопрос человеку.
*   **Никаких скрытых предположений:** Если задача, API используемых крейтов или контекст мультитенантности неясны до конца — остановись и спроси пользователя *до* генерации кода.
*   **Честность:** Если ты не уверен в логике или безопасности RLS-изоляции на 100% — прямо заяви об этом пользователю до вывода кода.
*   **Контроль коммитов:** Самостоятельно не делай git-коммитов в репозиторий, их делает исключительно человек.

## ✂️ 2. Точечные исправления (Surgical Changes)
*   **Хирургический подход:** Меняй только те строки, методы и файлы, которые напрямую связаны с текущим таском.
*   **Запрет на овер-инжиниринг:** Не переписывай функцию или модуль целиком, если достаточно точечного изменения одной строки.
*   **Уважение к чужому коду:** Не модифицируй работающие соседние модули, если они не входят в зону ответственности текущей задачи.

## 🚫 3. Что НЕЛЬЗЯ делать без согласования
1.  **Добавлять новую зависимость в `Cargo.toml`** — сначала обоснуй размер, влияние на компиляцию WASM, лицензию и отсутствие альтернатив.
2.  **Использовать `unsafe`** — запрещено. Исключения допускаются только в низкоуровневых WASM-мостах с обязательным комментарием `// SAFETY:` и ревью.
3.  **Менять публичные контракты данных в `crates/shared`** — это ломает синхронизацию между бэкендом и WASM-клиентом.
4.  **Нарушать изоляцию контента** — запрещено добавлять сквозной шеринг данных между разными `tenant_id` (см. `specs/DB_SCHEMA.md`).
5.  **Писать синхронный блокирующий код** в асинхронных пулах Tokio — это приводит к деградации СУБД-слоя.
6.  **Использовать `println!` или `panic!`** — только структурированное логирование через `tracing::*` и безопасный возврат `Result`.

## 📝 4. Документирование изменений (Knowledge-as-Code)
После написания нового кода знания о нем **обязательно** заносятся в соответствующий `.md`-файл в папке `specs/`.

*   **АКТУАЛИЗАЦИЯ КАРТЫ ПРОЕКТА:** При создании любого нового файла внутри `crates/` (нового модуля, компонента, папки) или изменении структуры ты **ОБЯЗАН** немедленно отразить это изменение в файле [`specs/STRUCTURE.md`](STRUCTURE.md). Структура каталогов и граф зависимостей в `STRUCTURE.md` должны на 100% соответствовать реальному содержимому репозитория.
*   **Новое архитектурное решение** → Обязательно создай **ADR** в директории `specs/decisions/[дата]-[номер].md` (формат даты: `гггг.мм.дд`, номер `0001` = следующий свободный, с обязательным указанием даты и времени фиксации в шапке документа и строкой в реестре `specs/decisions/README.md`).
*   **Изменение статуса реализации фичи** → Обнови статус в файле [`specs/STATUS.md`](STATUS.md) и внеси строку в журнал `CHANGELOG.md`.
*   **Новая ловушка рантайма/сборки** → Запиши ее в [`specs/GOTCHAS.md`](GOTCHAS.md).

## 📊 6. Метрики качества
*   **Размер крейта:** ≤ 1500 строк бизнес-логики (без учета тестов; см. `specs/STRUCTURE.md`).
*   **Размер файлов:** Маленькие файлы (200–300 строк), своевременная декомпозиция на подмодули.
*   **Покрытие тестами:** ≥ 80% для слоев аналитики и ETL-парсеров.
*   **WASM PWA бандл:** ≤ 2.0 MB gzip (включая рантайм Leptos и базовые верифицированные плагины; см. `specs/DEPLOY.md`).

## 💬 7. Специфика стека и Мультиязычность
*   **Локализация:** Текст интерфейса запрещено писать хардкодом в Rust-файлах. Создавай ключ в `src/locales/{ru,en}/messages.ftl` (Fluent-формат). Значение в `.ftl` должно быть обязательно переведено на оба языка (RU и EN).
*   **Обработка ошибок:** Ошибки серверных хостов реализуются через `anyhow`, внутренние библиотеки и SDK работают строго на типизированных перечислениях `thiserror` (см. `specs/CODING_STANDARDS.md`).
*   **Уведомления:** Единый канал обратной связи на фронтенде — вызов тостеров `toast_error(msg_key)` / `toast_success(msg_key)`. Уведомления `toast_success` запрещены для GET-запросов (только для мутаций).
