# Нефункциональные требования (NFR) и SLA

**Файл спецификации:** `NFR.md`

> **Статус документа.** Значения ниже — **стартовые целевые показатели** для этапа проектирования. Они уточняются по результатам нагрузочного тестирования на Этапе 5 (`SPECIFICATION.md` §10). До этого момента любые отклонения — не нарушение SLA, а материал для калибровки.
>
> Источники истины по смежным разделам: архитектура — [`ARCHITECTURE.md`](ARCHITECTURE.md); схема БД — [`DB_SCHEMA.md`](DB_SCHEMA.md); offline-лимиты — [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md); retention — [`STANDARDS.md`](STANDARDS.md) §«Политики удержания данных»; наблюдаемость — [`DIAGNOSTICS.md`](DIAGNOSTICS.md).

## 1. Доступность и восстановление (Availability & DR)

### 1.1. Целевая доступность (SLA)

| Поставка | Целевой uptime | Комментарий |
|:---|:---|:---|
| SaaS (мультитенант) | 99.9% в месяц | Исключая плановые окна обслуживания (не более 4 часов в месяц, с уведомлением за 7 дней). |
| On-Premise (Enterprise) | 99.5% в месяц | Зависит от инфраструктуры заказчика; SLA фиксируется в контракте. |
| Air-gapped On-Premise | По контракту | Платформа не управляет инфраструктурой; SLA на стороне заказчика. |

### 1.2. RTO / RPO

| Компонент | RTO | RPO | Механизм |
|:---|:---|:---|:---|
| Core-БД (PostgreSQL) | ≤ 15 минут | ≤ 5 минут | Streaming replication + WAL archiving (см. [`DEPLOY.md`](DEPLOY.md)). |
| LRS — Вариант А (TimescaleDB) | ≤ 30 минут | ≤ 15 минут | Репликация PostgreSQL + гипертаблицы; потеря последних чанков допустима. |
| LRS — Вариант Б (ClickHouse) | ≤ 60 минут | ≤ 30 минут | Репликация ClickHouse (ReplicatedMergeTree). |
| DAM (MinIO / S3) | ≤ 60 минут | ≤ 15 минут | Версионирование bucket + репликация. |
| Redis / River (очередь) | ≤ 15 минут | ≤ 5 минут | Persistence (AOF/RDB) для Redis; River хранится в PostgreSQL (см. RTO Core-БД). |

**Пояснение по LRS.** Потеря последних N минут xAPI-логов допустима, потому что PWA-клиент хранит их в `offline_xapi_statements` до получения подтверждения `200 OK` с массивом `accepted` (см. [`OPEN_API.md`](OPEN_API.md) §3.4). При потере серверных данных клиент повторно отправит пакет при следующей синхронизации. Это ключевое свойство: **LRS не является источником истины для офлайн-попыток** — источник истины временно живёт на клиенте.

## 2. Нагрузка (Concurrency & Throughput)

| Метрика | Целевое значение | Комментарий |
|:---|:---|:---|
| Одновременных активных пользователей (learner) на инстанс | 10 000 | Онлайн-сессии с открытыми вкладками. |
| Одновременных активных инструкторов / менторов | 200 | Одновременно работают в `cpanel`. |
| Одновременных администраторов тенантов | 50 | |
| Пропускная способность LRS (запись statements) | 5 000 statements/сек на инстанс | Усреднённо; пиково — до 20 000 (burst) с буферизацией. |
| Пропускная способность offline-синхронизации | 500 пакетов/сек | Пакет = до 100 statements. Соответствует 50 000 statements/сек в пике возврата студентов из офлайна. |
| ETL-импорт (пользователи) | 10 000 строк/сек | На один воркер; масштабируется горизонтально. |
| Одновременных WebSocket-подключений (чаты, прогресс) | 20 000 | На инстанс; при превышении — переход на SSE-фолбэк. |

**Масштабирование.** Значения указаны для одного инстанса. Горизонтальное масштабирование API-серверов и воркеров допускается и описано в [`ARCHITECTURE.md`](ARCHITECTURE.md) §5.1 (Подход 2).

## 3. Задержки (Latency Budgets)

Замеры — на стороне клиента, от отправки запроса до получения ответа, при нагрузке в пределах §2.

| Тип операции | p50 | p95 | p99 |
|:---|:---|:---|:---|
| Open API — чтение (`GET`) | ≤ 80 мс | ≤ 200 мс | ≤ 500 мс |
| Open API — запись (`POST`/`PATCH`) | ≤ 150 мс | ≤ 400 мс | ≤ 1 000 мс |
| Open API — экспорт LRS (стриминг) | ≤ 200 мс до первого байта | ≤ 500 мс | ≤ 1 500 мс |
| Offline-sync (`POST /analytics/lrs/sync`) | ≤ 200 мс | ≤ 600 мс | ≤ 1 500 мс |
| `#[server]` RPC-функции Leptos | ≤ 200 мс | ≤ 500 мс | ≤ 1 200 мс |
| Инициализация WASM-плагина (Контур Б) | ≤ 300 мс | ≤ 800 мс | ≤ 2 000 мс |
| Монтирование iframe-плагина (Контур А) | ≤ 500 мс | ≤ 1 200 мс | ≤ 3 000 мс |
| Выдача подписанного URL (`POST /content/signed-url`) | ≤ 30 мс | ≤ 100 мс | ≤ 300 мс |
| Первый рендер публичной страницы (SSR) | ≤ 400 мс | ≤ 1 000 мс | ≤ 2 500 мс |
| Гидратация клиентского WASM-бандла | ≤ 1 500 мс | ≤ 3 000 мс | ≤ 6 000 мс |

**Пояснение по SSR.** SSR-страницы не кэшируются для офлайна (см. [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §1). Их latency — это latency сервера, без учёта offline-сценариев.

## 5. Деградация (Graceful Degradation)

При превышении лимитов §2–§4 платформа деградирует по приоритетам:

1. **Отключение медиа-кэша** для офлайна — первым. Медиа остаётся доступным только онлайн (см. [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §3.2).
2. **Rate limit на ETL / SCIM** — вторым. Массовые импорты приостанавливаются, real-time provisioning продолжает работать.
3. **Rate limit на offline-sync** — третьим. Пакеты принимаются, но с задержкой; клиент повторяет попытку.
4. **Отключение WebSocket-чатов** — четвёртым, с переходом на SSE-фолбэк.
5. **Отключение необязательных фоновых задач** (аналитика, пересчёт прогресса) — пятым. LRS продолжает принимать statements.

Приоритет всегда: **запись xAPI → аутентификация → чтение контента → всё остальное.**

## 7. Наблюдаемость (Observability)

Обязательные метрики, которые должны быть экспортированы (формат — Prometheus / OpenTelemetry):

* **Latency (гистограммы):** по каждому эндпоинту из §3 — p50/p95/p99.
* **Throughput:** statements/сек, sync-пакетов/сек, ETL-строк/сек.
* **Ошибки:** 4xx/5xx по эндпоинтам; `dead_letter` вебхуков; `rejected` в offline-sync.
* **Ресурсы:** CPU, RAM, размер пула соединений PostgreSQL, размер очереди River/Redis, размер IndexedDB-очереди (клиентские метрики через RUM).
* **Бизнес-метрики:** количество активных тенантов, активных студентов, выданных сертификатов.

Правила логирования — в [`DIAGNOSTICS.md`](DIAGNOSTICS.md). Обязательные поля логов (`%tenant_id`, `%user_id`, `%batch_id`, `%statement_id`, `%job_id`) — там же, §1.

## 8. Безопасность (Performance Under Security)

* Все запросы к LRS проходят через RLS (Вариант А) или архитектурную изоляцию (Вариант Б) без исключений. Стоимость RLS-фильтра учтена в latency §3.
* Signed URLs и DRM (см. [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §3.1) не должны добавлять более 30 мс к p95 выдачи медиа.
* Валидация SCIM-запросов (RFC 7644) — не более 20 мс к p95.

## 9. Изменение NFR

Значения NFR — версионируемый артефакт. Изменение любого значения требует:
1. ADR в [`decisions/`](decisions/) с обоснованием.
2. Обновления этого файла.
3. Прогона нагрузочного теста (для изменений §2–§3).
4. Записи в [`CHANGELOG.md`](../CHANGELOG.md).
