# Соответствие отраслевым стандартам

> Источники истины по смежным разделам: схема метаданных — [`DB_SCHEMA.md`](DB_SCHEMA.md) §1.2; количественные лимиты (размер SCORM-пакета, медиа, IndexedDB) — [`NFR.md`](NFR.md); изоляция LRS — [`ARCHITECTURE.md`](ARCHITECTURE.md) §3.1.

## SCORM

Поддержка импорта SCORM 1.2 / 2004 (пакеты, манифесты `imsmanifest.xml`). Предусмотрено **два режима** работы с SCORM-пакетом — выбор режима определяется администратором тенанта на этапе импорта.

### Режим 1: Конвертация в нативную модель

* SCORM-пакет разбирается на этапе импорта: манифест `imsmanifest.xml` читается, ресурсы (HTML, JS, CSS, медиа) извлекаются, структура конвертируется в нативные юниты (`course_tree`) с сохранением порядка и вложенности.
* Трекинг — через внутренний LRS: события из SCORM-пакета транслируются в xAPI Statements по правилам маппинга (аналогично маппингу плагинов, см. [`PLUGIN.md`](PLUGIN.md) §5).
* SCORM API (`API_1484_11`) **не эмулируется** — пакет работает как обычный контент в нативном рантайме.
* **Офлайн:** работает как обычный нативный контент (текст, тесты, WASM-модули) в рамках границ [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §1.

### Режим 2: Runtime-режим (запуск как есть)

* SCORM-пакет запускается в изолированном `iframe` (аналогично Контуру А плагинов, см. [`PLUGIN.md`](PLUGIN.md) §2.1).
* SCORM API (`API` для 1.2, `API_1484_11` для 2004) эмулируется на стороне Ядра через `postMessage`-мост. Методы `Initialize`, `GetValue`, `SetValue`, `Commit`, `Terminate` проксируются в Ядро.
* Трекинг — через внутренний LRS: значения `cmi.*` маппятся в xAPI Statements.
* **Офлайн:** ограниченный режим. `Initialize` / `GetValue` работают из локального кэша; `SetValue` пишет в локальную очередь IndexedDB; `Commit` и `Terminate` выполняются при восстановлении сети. Полный SCORM-трекинг возможен только при онлайне.

### Ограничения и лимиты

* Максимальный размер SCORM-пакета, максимальное количество ресурсов, максимальный размер отдельного медиафайла — согласно [`NFR.md`](NFR.md).
* При превышении лимитов импорт отклоняется с явной ошибкой (`SCORM_PACKAGE_TOO_LARGE` / `SCORM_TOO_MANY_RESOURCES`), без падения по OOM.
* SCORM 2004 Sequencing & Navigation (полноценная поддержка правил последовательности) **не входит** в базовый скоуп; при необходимости реализуется как отдельное расширение.

## xAPI (Experience API)

Нативный формат телеметрии. Все учебные события пишутся в LRS в виде xAPI-стейтментов (JSON-LD). Поддерживается экспорт/импорт стейтментов, конфигурируемые профили (cmi5, video, assessment).

* Иммутабельный подход: все пришедшие statements сохраняются как независимые исторические факты (см. [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §5 и ADR [`2026.09.28-0002.md`](decisions/2026.09.28-0002.md)).
* LRS поддерживает два варианта хранения — TimescaleDB (RLS) и ClickHouse (архитектурная изоляция, см. [`DB_SCHEMA.md`](DB_SCHEMA.md) §2).

## LTI (Learning Tools Interoperability)

Поддержка LTI 1.3 (Core + Advantage) как **Tool Consumer** и как **Tool Provider**:

* как Consumer — встраивание внешних инструментов (конференции, интерактивные задания, симуляторы);
* как Provider — публикация курсов/модулей во внешние LMS (Moodle, Canvas, Blackboard).

## SCIM 2.0 (System for Cross-domain Identity Management)

Поддержка SCIM 2.0 (RFC 7643 / 7644) для автоматической синхронизации жизненного цикла пользователей с внешними HRIS/HRM-системами (Workday, SAP SuccessFactors, 1C:ЗУП).

* Эндпоинты `/scim/v2/Users` и `/scim/v2/Groups` — контракт фиксируется в [`OPEN_API.md`](OPEN_API.md) (Шаг K).
* SCIM — дополнение к кастомному ETL-мапперу (batch), а не замена: SCIM покрывает real-time provisioning, ETL — массовый импорт из файлов.
* Обработка offboarding: при удалении/деактивации пользователя через SCIM запускается автоматическое отчисление из активных `batches` (статус `dropped` в `batch_enrollments`) и анонимизация xAPI-логов по политике retention (см. §«Безопасность и приватность»).

## Доступность (a11y)

Целевой уровень — **WCAG 2.2 AA**. Требования распространяются на UI-крейт (`crates/ui`), публичный сайт, ЛК студента и панель управления. Проверки — axe-core в CI + ручной аудит ключевых сценариев (регистрация, прохождение курса, сдача задания).

* Автоматическая валидация контрастности пар «текст/фон» и «элемент UI/фон» (SC 1.4.3, SC 1.4.11) при сохранении `branding_config` тенанта. При провале — тенант получает предупреждение, сохранение палитры блокируется.
* Соответствие **WCAG 3.1 (Language of Page)** — см. §«Локализация».

## Локализация (i18n / l10n)

Платформа поддерживает мультиязычность на двух уровнях: интерфейс и метаданные контента.

### Языковая модель

* `tenants.default_locale` (BCP-47) — основной язык тенанта. Определяет локаль по умолчанию для новых пользователей и язык публичных страниц.
* `users.locale` (BCP-47, NULLable) — предпочтительная локаль пользователя. При отсутствии — наследуется от тенанта.
* Локали применяются к: интерфейсу, метаданным курсов/программ/тестов/заданий, форматам дат, чисел, валют.

### Метаданные контента

* В `programs`, `courses` — парные поля `title` / `title_i18n` (JSONB) и `description` / `description_i18n` (JSONB). Ключ — BCP-47: `{"ru": "…", "en": "…"}`.
* `title` (основной язык тенанта) используется для поиска и индексов; `title_i18n` — для отображения с учётом локали пользователя.
* Аналогично для `quizzes.title_i18n` и `assignments.title_i18n` / `instructions_text_i18n`.

### UI-строки

* Формат — **Fluent** (`src/locales/{locale}/messages.ftl`), согласовано с [`AGENTS.md`](AGENTS.md) §7.
* Обязательный минимум на этапе MVP — `ru` и `en`. Дополнительные локали добавляются по требованию тенанта.

### RTL

* Языки с письмом справа налево (арабский, иврит) поддерживаются на уровне UI-крейта: `dir="rtl"` на корневом элементе, зеркальные отступы, адаптация иконографики.
* Шрифты для RTL подключаются через Tailwind-конфигурацию; CSP-разрешения — в [`DEPLOY.md`](DEPLOY.md) §2.

### Локализация форматов

* Даты, числа, валюты, единицы измерения — через ICU-форматирование с учётом `users.locale`.
* Язык страницы (`<html lang="…">`) выставляется динамически — соответствует **WCAG 3.1 (Language of Page)**.

## Безопасность и приватность

### Соответствие GDPR / CCPA

* Экспорт данных субъекта: эндпоинт для выгрузки всех данных пользователя в машиночитаемом формате.
* Право на забвение: при удалении пользователя запускается каскад:
  * профиль (`users`) — удаляется;
  * xAPI-логи (`xapi_statements`) — **анонимизируются** (`actor_anonymized = TRUE`, `actor` заменяется на анонимный идентификатор), а не удаляются физически — для сохранения агрегированной аналитики тенанта. Срок хранения до анонимизации — согласно retention-политике.
  * чаты и комментарии — по политике тенанта (`delete` или `anonymize`);
  * сертификаты — сохраняются с `verification_hash` (публичная верификация остаётся возможной).
* Согласия: явное согласие на обработку данных при первом входе, лог согласий.

### Политики удержания данных (Retention Policies)

Политики задаются на уровне тенанта в таблице `retention_policies` (см. [`DB_SCHEMA.md`](DB_SCHEMA.md) §1.2). Дефолтные значения:

| Класс данных | Дефолтный срок | Действие по истечении |
|:---|:---|:---|
| `xapi_statements` | 730 дней (2 года) | `anonymize` |
| `audit_log` | 1095 дней (3 года) | `archive` |
| `chat_messages` | 365 дней (1 год) | `delete` |
| `etl_logs` | 90 дней | `delete` |
| `certificates` | Бессрочно | `keep` |

* Механика: cron-воркеры в `crates/server` читают `retention_policies` для каждого тенанта и применяют действие к строкам старше `retention_days`. Для `xapi_statements` действия выполняются на уровне TimescaleDB (drop chunks / update) или ClickHouse (`ALTER TABLE ... DELETE` по партициям).
* Тенант может переопределить дефолты в своём `retention_policies`; отключить класс данных полностью (`action = 'keep'`) разрешено только для `certificates`.
* Расширенный аудит (SIEM-интеграции, экспорт журналов) — в [`ROADMAP.md`](ROADMAP.md) §«Аудит и соответствие».
