# Соответствие отраслевым стандартам

> Источники истины по смежным разделам: схема метаданных — [`DB_SCHEMA.md`](DB_SCHEMA.md) §1.2; количественные лимиты (размер SCORM-пакета, медиа, IndexedDB) — в [`NFR.md`](NFR.md); изоляция LRS — в [`ARCHITECTURE.md`](ARCHITECTURE.md) §3.1; инфраструктура и Data Residency — в [`DEPLOY.md`](DEPLOY.md) §4; Conformance Test Suite — в §«Conformance Testing» этого файла; иммутабельность LRS — в ADR [`2026.09.28-0002.md`](decisions/2026.09.28-0002.md).

## SCORM

Поддержка импорта SCORM 1.2 / 2004 (пакеты, манифесты `imsmanifest.xml`). Предусмотрено **два режима** работы с SCORM-пакетом — выбор режима определяется администратором тенанта на этапе импорта.

### Режим 1: Конвертация в нативную модель (без эмуляции SCORM API)

**Область применения:** сторонние стандартные SCORM-пакеты, у которых нет собственного трекинга через `cmi.*`, либо для которых детальный трекинг не критичен.

* SCORM-пакет разбирается на этапе импорта: манифест `imsmanifest.xml` читается, структура (`organization` / `item`) конвертируется в нативные юниты (`course_tree`) с сохранением порядка и вложенности.
* **Ресурсы извлекаются и сохраняются:** HTML, JS, CSS, медиа — все файлы пакета распаковываются и размещаются в DAM-хранилище тенанта. Нативный JavaScript SCORM-пакета **выполняется** в изолированном sandboxed-контейнере (iframe с `sandbox="allow-scripts"`, без `allow-same-origin`) — аналогично Контуру А плагинов (см. [`PLUGIN.md`](PLUGIN.md) §2.1). Это позволяет работать интерактивным SCORM-модулям, завязанным на собственный JS.
* **SCORM API не эмулируется.** Объекты `API` (для SCORM 1.2) и `API_1484_11` (для SCORM 2004) в контейнере не создаются. Пакет работает как автономный интерактивный контент **без обмена `cmi.*`** с ядром.
* **Трекинг ограничен.** Для сторонних стандартных SCORM-пакетов фиксируется только **факт открытия/закрытия юнита** и завершение по таймауту. Детальный трекинг прогресса (`cmi.core.lesson_status`, `cmi.suspend_data`, `cmi.interactions`) **не передаётся** в LRS.
* **Офлайн:** работает как обычный нативный контент в рамках границ [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §1 (текст, встроенные ресурсы, WASM-модули). Так как SCORM API не эмулируется, офлайн-режим не требует серверного обмена `cmi.*`.

> **Что теряется в Режиме 1.** Если SCORM-пакет рассчитан на полноценный обмен `cmi.*` с LMS (сохранение состояния, оценок, взаимодействий через `SetValue`/`Commit`), этот обмен **не поддерживается**. Для таких пакетов используется Режим 2 (Runtime).

#### Собственные (референсные) SCORM-пакеты платформы

Для **собственных** SCORM-пакетов платформы (референсные Enterprise-модули), разработанных самой командой платформы, допускается **интеграция через кастомный `sendEvent`** (мост `postMessage`) для передачи детализированных событий в LRS по правилам маппинга (аналогично маппингу плагинов, см. [`PLUGIN.md`](PLUGIN.md) §5).

Это **не является** стандартным поведением SCORM и не распространяется на сторонние пакеты. Собственные пакеты платформы дополнены интеграционным слоем, специфичным для нашего ядра, что позволяет получить детальный трекинг без эмуляции `API_1484_11`.

### Режим 2: Runtime-режим (запуск как есть, с эмуляцией API)

**Область применения:** сторонние стандартные SCORM-пакеты, которым требуется полноценный обмен `cmi.*` с LMS.

* SCORM-пакет запускается в изолированном `iframe` (аналогично Контуру А плагинов, см. [`PLUGIN.md`](PLUGIN.md) §2.1).
* **SCORM API эмулируется** на стороне Ядра через `postMessage`-мост. Методы `Initialize`, `GetValue`, `SetValue`, `Commit`, `Terminate` (а также legacy-варианты для SCORM 1.2) проксируются в Ядро.
* **Трекинг — через внутренний LRS.** Значения `cmi.*` маппятся в xAPI Statements по стандартному профилю cmi5 / ADL.
* **Офлайн:** ограниченный режим. `Initialize` / `GetValue` работают из локального кэша; `SetValue` пишет в локальную очередь IndexedDB; `Commit` и `Terminate` выполняются при восстановлении сети. Полный SCORM-трекинг возможен только при онлайне.
* **Выбор режима.** Администратор тенанта выбирает режим на этапе импорта. По умолчанию — Режим 1 (конвертация).
  * **Режим 2 рекомендуется** для SCORM-пакетов, использующих `cmi.*` для интерактивной логики (ветвление, адаптивные тесты, ветвление по `cmi.core.lesson_status`), а также для любых пакетов, где требуется детальный трекинг прогресса в LRS.
  * **Если пакет содержит вызовы `API` / `API_1484_11` и зависит от `cmi.*`,** при импорте в Режиме 1 платформа выводит предупреждение в UI и рекомендует выбрать Режим 2. Импорт в Режиме 1 в этом случае возможен, но детальный трекинг работать не будет.

### Сравнение режимов

| Характеристика | Режим 1 (конвертация) | Режим 2 (runtime) |
|:---|:---|:---|
| SCORM API | Не эмулируется | Эмулируется |
| Детальный трекинг `cmi.*` | Нет (для сторонних) / Да (для собственных через `sendEvent`) | Да |
| Интерактивный JS пакета | Работает | Работает |
| Офлайн | Полный (как нативный контент) | Ограниченный (буфер в IndexedDB) |
| Рекомендуется для | Сторонних пакетов без `cmi.*`; собственных референсных пакетов | Сторонних пакетов с интерактивной логикой на `cmi.*` |

### Ограничения и лимиты

* Максимальный размер SCORM-пакета, максимальное количество ресурсов, максимальный размер отдельного медиафайла — согласно [`NFR.md`](NFR.md).
* При превышении лимитов импорт отклоняется с явной ошибкой (`SCORM_PACKAGE_TOO_LARGE` / `SCORM_TOO_MANY_RESOURCES`), без падения по OOM.
* SCORM 2004 Sequencing & Navigation (полноценная поддержка правил последовательности) **не входит** в базовый скоуп; при необходимости реализуется как отдельное расширение (см. [`ROADMAP.md`](ROADMAP.md) §«Планируемые направления»).

### Доступность (a11y) SCORM-пакетов

* **Контейнер** (iframe + обвязка Ядра) соответствует WCAG 2.2 AA: навигация с клавиатуры к iframe, `lang` для RTL, фокус, контраст управляющих элементов.
* **Содержимое стороннего SCORM-пакета платформа не контролирует.** Соответствие WCAG 2.2 AA содержимого — ответственность разработчика пакета.
* При импорте SCORM-пакета тенант получает **предупреждение** в UI: «Сторонние SCORM-пакеты не проверяются платформой на соответствие WCAG 2.2 AA. Убедитесь, что содержимое доступно вашим пользователям».
* Для **собственных** SCORM-пакетов платформы (референсные Enterprise-модули) требования WCAG 2.2 AA применяются в полном объёме — как к нативному контенту.

## xAPI (Experience API)

Нативный формат телеметрии. Все учебные события пишутся в LRS в виде xAPI-стейтментов (JSON-LD). Поддерживается экспорт/импорт стейтментов, конфигурируемые профили (cmi5, video, assessment).

### Append-only подход и иммутабельность

LRS спроектирован по принципу **append-only на уровне приложения**:

* При обычной работе события **не перезаписываются и не удаляются**: каждое новое событие добавляется как отдельная запись.
* Конфликтующие события (например, попытки с разных устройств) сохраняются полностью — без стратегии Last Write Wins (см. [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §5 и ADR [`2026.09.28-0002.md`](decisions/2026.09.28-0002.md)).
* Идемпотентность записи обеспечивается по `statement_id`: `INSERT ... ON CONFLICT DO NOTHING` (TimescaleDB) или batch-`SELECT` + `INSERT` (ClickHouse) — см. [`OPEN_API.md`](OPEN_API.md) §3.4.

**Исключение — retention-анонимизация.** В строгом соответствии с политиками удержания (см. §«Политики удержания данных») и требованиями GDPR / 152-ФЗ выполняется **процедурная анонимизация** PII:

* `actor` в statement заменяется на анонимный идентификатор;
* флаг `actor_anonymized` устанавливается в `TRUE`;
* структура события и агрегированные метрики (score, success, duration) **сохраняются** — целостность исторических фактов обучения не нарушается.

Это **не** нарушает append-only в смысле бизнес-процесса: событие не перезаписывается для изменения результата, а лишь маскируется персональная идентификация.

### LRS: TimescaleDB vs ClickHouse

LRS поддерживает два варианта хранения:

* **Вариант А (TimescaleDB):** нативная RLS, гипертаблицы, дешёвые мутации. Рекомендуется для коробочных поставок с требованиями строгого ИБ-аудита.
* **Вариант Б (ClickHouse):** архитектурная изоляция (без RLS), колоночное хранение, **тяжёлые асинхронные мутации** при retention-анонимизации. Рекомендуется для экстремальных нагрузок.

Детали — в [`DB_SCHEMA.md`](DB_SCHEMA.md) §2.

### Conformance

Соответствие xAPI LRS проверяется через **xAPI LRS Conformance Test Suite** (ADL) — входит в комплект поставки (см. §«Conformance Testing»).

## LTI (Learning Tools Interoperability)

Поддержка LTI 1.3 (Core + Advantage) как **Tool Consumer** и как **Tool Provider**:

* как Consumer — встраивание внешних инструментов (конференции, интерактивные задания, симуляторы);
* как Provider — публикация курсов/модулей во внешние LMS (Moodle, Canvas, Blackboard).

## SCIM 2.0 (System for Cross-domain Identity Management)

Поддержка SCIM 2.0 (RFC 7643 / 7644) для автоматической синхронизации жизненного цикла пользователей с внешними HRIS/HRM-системами (Workday, SAP SuccessFactors, 1C:ЗУП).

* Эндпоинты `/scim/v2/Users` и `/scim/v2/Groups` — контракт в [`OPEN_API.md`](OPEN_API.md) §3.5.
* SCIM — дополнение к кастомному ETL-мапперу (batch), а не замена: SCIM покрывает real-time provisioning, ETL — массовый импорт из файлов.
* Обработка offboarding: при удалении/деактивации пользователя через SCIM запускается автоматическое отчисление из активных `batches` (статус `dropped` в `batch_enrollments`) и анонимизация xAPI-логов по политике retention (см. §«Безопасность и приватность»).

## Доступность (a11y)

Целевой уровень — **WCAG 2.2 AA**. Требования распространяются на:

* UI-крейт (`crates/ui`);
* публичный сайт (`website`);
* личный кабинет студента (`student`);
* панель управления (`cpanel`);
* **собственные** SCORM-пакеты и WASM-плагины Контура Б платформы (референсные Enterprise-модули).

**Область, на которую требования WCAG 2.2 AA не распространяются напрямую:**

* **Сторонние SCORM-пакеты** в Режиме 2 (Runtime) — платформа обеспечивает доступный контейнер, но не содержимое (см. §SCORM «Доступность»).
* **Сторонние iframe-плагины Контура А** — аналогично: контейнер доступен, содержимое — на стороне разработчика. Требования к a11y для разработчиков — в [`PLUGIN_DEVELOPMENT_TEMPLATE.md`](PLUGIN_DEVELOPMENT_TEMPLATE.md).

Проверки — axe-core в CI + ручной аудит ключевых сценариев (регистрация, прохождение курса, сдача задания). Расширенное a11y-тестирование (Playwright + NVDA/VoiceOver, внешний аудит WCAG 2.2 AA) — в [`ROADMAP.md`](ROADMAP.md) §«Расширенное a11y-тестирование».

* Автоматическая валидация контрастности пар «текст/фон» и «элемент UI/фон» (SC 1.4.3, SC 1.4.11) при сохранении `branding_config` тенанта. При провале — тенант получает предупреждение, сохранение палитры блокируется.
* Соответствие **WCAG 3.1 (Language of Page)** — см. §«Локализация».

## Локализация (i18n / l10n)

Платформа поддерживает мультиязычность на двух уровнях: интерфейс и метаданные контента.

### Языковая модель

* `tenants.default_locale` (BCP-47) — основной язык тенанта. Определяет локаль по умолчанию для новых пользователей и язык публичных страниц.
* `users.locale` (BCP-47, NULLable) — предпочтительная локаль пользователя. При отсутствии — наследуется от тенанта.
* Локали применяются к: интерфейсу, метаданным курсов/программ/тестов/заданий, форматам дат, чисел, валют.

### Метаданные контента

* В `programs`, `courses` — парные поля `title` / `title_i18n` (JSONB) и `description` / `description_i18n` (JSONB). Ключ — BCP-47: `{"ru": "…", "en": "…"}`.
* `title` (основной язык тенанта) используется для поиска и индексов; `title_i18n` — для отображения с учётом локали пользователя.
* Аналогично для `quizzes.title_i18n` и `assignments.title_i18n` / `instructions_text_i18n`.

### UI-строки

* Формат — **Fluent** (`src/locales/{locale}/messages.ftl`), согласовано с [`AGENTS.md`](AGENTS.md) §7.
* Обязательный минимум на этапе MVP — `ru` и `en`. Дополнительные локали добавляются по требованию тенанта.

### RTL

* Языки с письмом справа налево (арабский, иврит) поддерживаются на уровне UI-крейта: `dir="rtl"` на корневом элементе, зеркальные отступы, адаптация иконографики.
* Шрифты для RTL подключаются через Tailwind-конфигурацию; CSP-разрешения — в [`DEPLOY.md`](DEPLOY.md) §2.

### Локализация форматов

* Даты, числа, валюты, единицы измерения — через ICU-форматирование с учётом `users.locale`.
* Язык страницы (`<html lang="…">`) выставляется динамически — соответствует **WCAG 3.1 (Language of Page)**.

## Data Portability (Портативность данных)

Для Enterprise- и госсектора критично, чтобы заказчик мог выгрузить данные из платформы в стандартных форматах и мигрировать в другую LMS без потери информации. Платформа поддерживает экспорт в следующих форматах.

### Форматы экспорта

| Класс данных | Формат | Статус |
|:---|:---|:---|
| **Пользователи, курсы, зачисления, оценки** | IMS Global OneRoster (CSV / ZIP) | Планируется в 1.x (см. [`ROADMAP.md`](ROADMAP.md) §«Data Portability»). |
| **Тесты (Quizzes)** | QTI 2.1 (Question and Test Interoperability) | Планируется; в MVP — не поддерживается. |
| **xAPI-логи (учебный след)** | Нативный JSON-LD (соответствует спецификации xAPI) | ✅ Поддерживается (основной формат LRS). |
| **Сертификаты** | `verification_hash` + публичный API верификации; экспорт метаданных в JSON. | ✅ Поддерживается. |
| **Оценки (для интеграции)** | LTI Advantage AGS (Assignment and Grade Services) | Планируется как интеграция с внешними LMS (не экспорт). |
| **GDPR-экспорт данных субъекта** | ZIP с полной выгрузкой (форматы: JSON, CSV для табличных данных, JSON-LD для xAPI). | ✅ Поддерживается (см. §«Соответствие GDPR / CCPA»). |

### Импорт

| Класс данных | Формат | Статус |
|:---|:---|:---|
| **Пользователи** | CSV / XLSX / XML / JSON (Custom ETL) + SCIM 2.0 (real-time) | ✅ Поддерживается. |
| **Курсы и контент** | SCORM 1.2 / 2004, cmi5 | ✅ Поддерживается (см. §SCORM). |
| **Тесты (Quizzes)** | QTI 2.1 | Планируется. |
| **xAPI-логи** | JSON-LD | Импорт не имеет смысла: LRS — append-only, события не мигрируют между инстансами. |

### Ограничения

* **OneRoster** — поддерживается экспорт только для пользователей, курсов, зачислений и оценок. Структура `course_tree` (нативная иерархия юнитов) не маппится на OneRoster — экспортируется как отдельный JSON.
* **QTI** — если реализуется, то только экспорт Quizzes; задания с ручной проверкой (Assignments) не входят в QTI.
* **LTI AGS** — это интеграция для обмена оценками в реальном времени, а не формат экспорта.

Реализация расширенных форматов (OneRoster, QTI, LTI AGS) вынесена за MVP — см. [`ROADMAP.md`](ROADMAP.md) §«Data Portability».

## Conformance Testing

Для коробочных поставок администратор заказчика должен иметь возможность самостоятельно проверить корректность импорта контента и соответствие стандартам. Для этого в комплект поставки входит **Conformance Test Suite**.

### Что входит в комплект

* **CLI `rust-lms-conformance`** — утилита командной строки для запуска проверок локально.
* **Сервис `rust-lms-conformance-tests`** (опционально, для SaaS и крупных On-Premise) — веб-интерфейс, доступный администратору, для запуска тех же проверок через UI.

### Что проверяется

| Стандарт | Набор проверок | Источник |
|:---|:---|:---|
| SCORM 1.2 | ADL SCORM 1.2 Test Suite | ADL |
| SCORM 2004 | ADL SCORM 2004 Test Suite | ADL |
| cmi5 | cmi5 Test Suite | ADL |
| xAPI LRS | xAPI LRS Conformance Test Suite | ADL |
| LTI 1.3 | LTI 1.3 Conformance Test Suite | 1EdTech |
| SCIM 2.0 | SCIM 2.0 Test Suite | RFC 7643 / 7644 |

### Как использовать

* **CLI:** администратор запускает `rust-lms-conformance scorm --package <path>` для проверки SCORM-пакета перед импортом. Результат — JSON-отчёт с перечнем пройденных/непройденных проверок.
* **Сервис:** в админ-панели `cpanel` — раздел «Conformance Testing»: загрузка пакета, выбор стандарта, запуск, просмотр отчёта.
* **Импорт:** при импорте SCORM-пакета платформа автоматически прогоняет базовые проверки (валидность манифеста, целостность ресурсов). При провале — предупреждение, но не блокировка (тенант решает, продолжать ли импорт).

### Что НЕ входит в базовый скоуп

* Автоматическая **сертификация** контента — платформа не выдаёт сертификат соответствия; результаты проверок носят рекомендательный характер.
* Полная реализация SCORM 2004 Sequencing & Navigation — см. [`ROADMAP.md`](ROADMAP.md) §«Планируемые направления».

### Хранение

* CLI и сервис входят в дистрибутив (см. [`DEPLOY.md`](DEPLOY.md) §3). В Air-gapped работают локально, без внешних вызовов.
* Отчёты сохраняются в `audit_log` (структурированно) и, опционально, выгружаются в DAM для аудита.

## Безопасность и приватность

### Соответствие GDPR / CCPA

* Экспорт данных субъекта: эндпоинт для выгрузки всех данных пользователя в машиночитаемом формате (форматы — см. §«Data Portability»).
* Право на забвение: при удалении пользователя запускается каскад:
  * профиль (`users`) — удаляется;
  * xAPI-логи (`xapi_statements`) — **анонимизируются** (`actor_anonymized = TRUE`, `actor` заменяется на анонимный идентификатор), а не удаляются физически — для сохранения агрегированной аналитики тенанта. Срок хранения до анонимизации — согласно retention-политике.
  * чаты и комментарии — по политике тенанта (`delete` или `anonymize`);
  * сертификаты — сохраняются с `verification_hash` (публичная верификация остаётся возможной).
* Согласия: явное согласие на обработку данных при первом входе, лог согласий.

### Application-Level Encryption (ALE)

Для тенантов с повышенными требованиями (госсектор, крупные корпорации, обработка PII) платформа поддерживает шифрование чувствительных полей на уровне приложения — в дополнение к шифрованию на уровне СУБД (TDE) и TLS.

* **Область применения (по умолчанию):**
  * `users.email`, `users.first_name`, `users.last_name`, `users.external_id`;
  * поля внутри `users.metadata`, помеченные как PII (декларативно, через схему профиля ETL).
* **Область применения (опционально, по требованию тенанта):** `chat_messages.content`, `assignments.instruction_text`.
* **Схема шифрования (envelope encryption):**
  * **DEK (Data Encryption Key)** — уникальный для тенанта, шифрует PII-поля (AES-256-GCM).
  * **KEK (Key Encryption Key)** — шифрует DEK; хранится в KMS / Vault.
  * Ротация DEK — по расписанию (по умолчанию раз в год; конфигурируется тенантом). Ротация KEK — по регламенту инфраструктуры (см. [`DEPLOY.md`](DEPLOY.md) §4.4).
* **Поиск по зашифрованным полям:**
  * `email` — **детерминированное шифрование** (AES-SIV) или blind index (HMAC от нормализованного email) для поиска по точному значению. Диапазонный поиск по email не поддерживается и не требуется.
  * `external_id` — аналогично `email`.
  * `first_name` / `last_name` — без поиска (используются только для отображения); поиск по ФИО не поддерживается.
* **Опциональность:** ALE — настраиваемая опция на уровне тенанта. Включение требует решения администратора тенанта; отключение не удаляет уже зашифрованные данные (требуется отдельная миграция).
* **Стоимость:** ALE добавляет задержку на шифрование/дешифрование. Бюджет — в [`NFR.md`](NFR.md) §8.
* **Управление ключами:** все операции с DEK/KEK (генерация, ротация, бэкап, аудит) — в [`DEPLOY.md`](DEPLOY.md) §4.4.

### Data Residency и суверенитет данных

* **Размещение данных.** Для каждого тенанта явно фиксируется регион размещения:
  * Core-БД (PostgreSQL),
  * LRS (TimescaleDB / ClickHouse),
  * DAM (MinIO / S3),
  * бэкапы всех компонентов,
  * KMS / Vault с ключами шифрования.
* **Запрет трансграничной передачи.** Данные тенанта не покидают выбранный регион без явного согласия тенанта (фиксируется в контракте). Резервные копии хранятся в том же регионе.
* **Соответствие 152-ФЗ (РФ).** Для тенантов, обрабатывающих персональные данные граждан РФ:
  * хранение PII на территории РФ (Core-БД, DAM);
  * шифрование бэкапов;
  * KMS в том же регионе;
  * уведомление Роскомнадзора об обработке ПДн — на стороне тенанта (оператора ПДн); платформа предоставляет технические средства.
* **Air-gapped On-Premise.** Все данные и ключи находятся на инфраструктуре заказчика; трансграничная передача отсутствует по определению. Детали — в [`DEPLOY.md`](DEPLOY.md) §4.
* **SaaS-поставка.** Регион размещения выбирается при provisioning тенанта; миграция тенанта между регионами — отдельная процедура с аудитом (не автоматическая). Процедура описана в ADR [`2026.09.29-0005.md`](decisions/2026.09.29-0005.md).
* **Аудит.** Все операции с ключами шифрования и миграции данных между регионами фиксируются в `audit_log` (см. [`DIAGNOSTICS.md`](DIAGNOSTICS.md) §1).

### Политики удержания данных (Retention Policies)

Политики задаются на уровне тенанта в таблице `retention_policies` (см. [`DB_SCHEMA.md`](DB_SCHEMA.md) §1.2). Дефолтные значения:

| Класс данных | Дефолтный срок | Действие по истечении |
|:---|:---|:---|
| `xapi_statements` | 730 дней (2 года) | `anonymize` |
| `audit_log` | 1095 дней (3 года) | `archive` |
| `chat_messages` | 365 дней (1 год) | `delete` |
| `etl_logs` | 90 дней | `delete` |
| `certificates` | Бессрочно | `keep` |

* Механика: cron-воркеры в `crates/server` читают `retention_policies` для каждого тенанта и применяют действие к строкам старше `retention_days`. Для `xapi_statements` действия выполняются на уровне TimescaleDB (drop chunks / update) или ClickHouse (`ALTER TABLE ... DELETE` / `UPDATE` по партициям).
* **Нюанс ClickHouse:** мутации асинхронны и ресурсоёмки. Для крупных инсталляций рекомендуется выполнять анонимизацию в окна низкой нагрузки с мониторингом `system.mutations` или использовать паттерн «холодный архив» (перенос старых партиций в отдельное хранилище). Детали — в [`DB_SCHEMA.md`](DB_SCHEMA.md) §2 Вариант Б «Мутации и retention-анонимизация в ClickHouse».
* Тенант может переопределить дефолты в своём `retention_policies`; отключить класс данных полностью (`action = 'keep'`) разрешено только для `certificates`.
* Расширенный аудит (SIEM-интеграции, экспорт журналов) — в [`ROADMAP.md`](ROADMAP.md) §«Аудит и соответствие».
