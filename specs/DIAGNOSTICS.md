# Диагностика, Сквозное логирование и Профилирование

Поскольку платформа является высоконагруженной и мультитенантной, отладка подчиняется строгим правилам логирования, исключающим утечку данных между организациями.

> Источники истины по упоминаемым сущностям: [`CODING_STANDARDS.md`](CODING_STANDARDS.md) §1.5 (правила `tracing`), [`ARCHITECTURE.md`](ARCHITECTURE.md) §3.4 (иммутабельная хронология LRS), [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §4–5 (Sync Manager и разрешение конфликтов), [`OPEN_API.md`](OPEN_API.md) §3.2 (`job_id` ETL) и §4.3 (`dead_letter` вебхуков). Инфраструктура OTel — в [`DEPLOY.md`](DEPLOY.md) §3. Бюджеты производительности — в [`NFR.md`](NFR.md) §7–8.

## 1. Контекст логирования (Structured Tracing)

* **Обязательные структурные поля.** Каждый лог, порождаемый бэкендом (включая `api`, `server` и фоновые воркеры), обязан содержать структурные поля `%tenant_id` и `%user_id`. Поле `%batch_id` — обязательно, если операция происходит в контексте потока обучения. Поля добавляются через макросы `tracing::*` (см. [`CODING_STANDARDS.md`](CODING_STANDARDS.md) §1.5).
* **Запрет неструктурированного склеивания строк.** Использование подстановки форматирования в сообщениях логов запрещено — все переменные передаются как именованные поля макроса.
* **Сквозная корреляция LRS-операций.** Для любой операции, связанной с записью или чтением xAPI statements (включая офлайн-синхронизацию и расчёт прогресса), в лог обязаны попадать:
  * `%statement_id` — уникальный идентификатор statement (UUID v4, генерируется на клиенте, см. [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §2.2);
  * `%timestamp` — исходное время совершения действия на устройстве;
  * `%stored_at` — серверное время записи в LRS.
  Эти три поля — минимальный набор для воспроизведения инцидентов офлайн-синхронизации и разбора конфликтующих попыток (см. ADR [`2026.09.28-0002.md`](decisions/2026.09.28-0002.md) и [`ARCHITECTURE.md`](ARCHITECTURE.md) §3.4).
* **Сквозная корреляция ETL-операций.** Логи фоновых импортов обязаны содержать `%job_id` — идентификатор мета-задачи, возвращаемый эндпоинтом `POST /api/v1/users/import-custom` (см. [`OPEN_API.md`](OPEN_API.md) §3.2).
* **Корреляция с распределённым трейсингом.** Все структурные поля выше обязаны быть **атрибутами span** в OpenTelemetry (см. §4). Логи и трейсы используют одну и ту же систему идентификаторов: `%trace_id` и `%span_id` попадают в лог автоматически через `tracing-opentelemetry`.

## 2. Диагностические профили воркеров фоновых задач

* **Метрики производительности ETL.** Тяжелые импорты логируют метрики каждые 500 обработанных строк: объём занимаемой RAM, время трансформации чанка и количество ошибок валидации. Каждая запись сопровождается `%job_id` и `%tenant_id`.
* **Защита персональных данных (GDPR/ФЗ-152).** Логи ошибок маппинга полей не должны содержать персональные данные пользователей — вместо ФИО логируются индексы строк и типы нарушений схем.
* **Ретраи и отказы.** При срабатывании политики Exponential Backoff (см. [`ARCHITECTURE.md`](ARCHITECTURE.md) §5.3) лог фиксирует номер попытки, тип ошибки и планируемое время следующего запуска. При переводе задачи в `dead_letter` (см. [`OPEN_API.md`](OPEN_API.md) §4.3) пишется отдельная запись уровня `error` с указанием причины.

## 3. Отладка Service Workers и IndexedDB на фронтенде

* **Префикс и канал.** Фоновый Sync Manager PWA пишет логи миграции состояний очереди во внутреннюю консоль браузера с префиксом `[PWA-SYNC]`. Для каждой записи указывается `%statement_id` (для xAPI-очереди) или `%composite_key` (для `offline_plugin_state`).
* **Статусы очереди.** Service Worker переводит статус очереди в одно из состояний: `RUNNING`, `SUSPENDED`, `DRAINING`, `ERROR`. Переход в `SUSPENDED` происходит при потере сети или ошибке авторизации токенов; в `ERROR` — при постоянном отказе бэкенда принимать пакет после исчерпания ретраев. Статус выставляется диагностическим флагом, считываемым Leptos-интерфейсом.
* **Корреляция клиент–сервер.** `statement_id`, сгенерированный на клиенте, обязан сохраняться в клиентских логах `[PWA-SYNC]` и в серверных логах LRS-операций (см. §1). Это единственный способ связать «клиент поставил в очередь» и «сервер принял в LRS» при разборе инцидентов.

## 4. Распределённый трейсинг (OpenTelemetry)

Платформа использует **OpenTelemetry (OTel)** как стандарт распределённого трейсинга и метрик. Это дополняет структурированное логирование (§1), а не заменяет его.

### 4.1. Архитектура

* **SDK в крейтах.** Инструментирование выполняется в `api`, `server` и `client` (WASM) через `tracing-opentelemetry` + `opentelemetry-otlp`. Автоматическое инструментирование: `axum` (HTTP-сервер), `sqlx` (SQL-запросы), `reqwest` (исходящие HTTP), `redis`/`clickhouse` (клиенты СУБД).
* **OTLP-экспорт.** Трейсы и метрики экспортируются по протоколу **OTLP/gRPC** на OTel Collector. Collector маршрутизирует данные в backend (см. ниже) и отвечает за батчинг, ретраи, семплирование.
* **Backend.** Поддерживаются любые OTLP-совместимые системы: Grafana Tempo, Jaeger, OpenSearch, Datadog, Elastic APM. Выбор — на этапе развертывания (см. [`DEPLOY.md`](DEPLOY.md) §3).
* **Air-gapped.** OTel Collector разворачивается локально внутри закрытого контура. Экспорт во внешние SaaS-системы запрещён. Backend — из перечня локально поддерживаемых.

### 4.2. Обязательные атрибуты span

Каждый span обязан содержать те же структурные поля, что и логи (§1):

* `tenant_id` — обязательно для всех span, кроме инфраструктурных (например, provisioning тенанта).
* `user_id` — обязательно, если операция совершается от имени пользователя.
* `batch_id` — обязательно, если операция в контексте потока обучения.
* `statement_id` — обязательно для LRS-операций (запись/чтение xAPI statements).
* `job_id` — обязательно для ETL-операций и фоновых воркеров.
* `http.method`, `http.route`, `http.status_code` — для HTTP-span (генерируются автоматически).
* `db.system`, `db.operation` — для SQL-span (генерируются автоматически).

### 4.3. Семплирование (Sampling)

* **Head-based sampling:**
  * В production — 10% от общего числа трейсов по умолчанию.
  * Для операций с `%job_id` (ETL) — 100% (это редкие и важные операции).
  * Для операций с ошибками (`status = ERROR`) — 100% (tail-based sampling в Collector).
* **Tail-based sampling (в OTel Collector):**
  * Трейсы с ошибками — 100%.
  * Трейсы длительностью > p99 (по метрикам) — 100%.
  * Остальные — по head-based.
* **Конфигурация:** значения по умолчанию в `config.toml`. Переопределяются на уровне тенанта только в сторону увеличения (для диагностики инцидентов).

### 4.4. Корреляция с клиентским RUM

* Клиентский WASM-бандл экспортирует RUM-метрики (Core Web Vitals: LCP, INP, CLS) и трассировку критичных операций (например, offline-sync) через OTel JS SDK.
* Клиентские трейсы коррелируются с серверными через `traceparent` HTTP-заголовок (W3C Trace Context).
* `statement_id`, сгенерированный на клиенте, обязательно попадает в клиентский span и в серверный span LRS-операции — это позволяет собрать полный трейс «клиент → offline-очередь → синхронизация → запись в LRS».

### 4.5. Что не попадает в трейсы

* Персональные данные (ФИО, email, содержимое чатов) — запрещено добавлять в атрибуты span, как и в логи (§2).
* Секреты (токены, пароли, ключи) — запрещено; при необходимости используются хэши или идентификаторы.
* Полные SQL-запросы с параметрами — только с плейсхолдерами, без значений.
