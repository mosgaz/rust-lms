# Концепция Модульной LMS-платформы

(Enterprise-grade Interoperable & Pluggable LMS)

> Сводная архитектурная картина — в [`ARCHITECTURE.md`](ARCHITECTURE.md). Профильные источники истины: [`DB_SCHEMA.md`](DB_SCHEMA.md), [`OPEN_API.md`](OPEN_API.md), [`PLUGIN.md`](PLUGIN.md), [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md), [`STANDARDS.md`](STANDARDS.md), [`COMMUNICATIONS.md`](COMMUNICATIONS.md), [`CONFERENCING.md`](CONFERENCING.md).

## 1. Введение и Цели

Создание универсальной образовательной платформы, сочетающей гибкость конструктора, мощь корпоративных стандартов интеграции и возможность автономной работы как на стороне клиента (офлайн-режим), так и в полностью изолированных серверных контурах.

Ключевые отличия от классических LMS:

* **Плагиноориентированная архитектура (Core + Micro-apps):** Предметная логика полностью вынесена в изолированные микроприложения. Ядро системы не содержит логики конкретных дисциплин, оно предоставляет контекст выполнения, стандартизированный UI-кит и сквозные инструменты коммуникации.
* **Двухуровневая изоляция плагинов:** Гибридная модель запуска расширений (безопасный изолированный iframe для внешних/непроверенных модулей и сверхпроизводительный нативный WebAssembly для верифицированных инструментов).
* **Архитектура Offline-First PWA:** Платформа разворачивается как прогрессивное веб-приложение, предоставляя нативный пользовательский опыт на мобильных и десктопных устройствах с возможностью полноценного обучения, сбора учебного следа и работы WASM-плагинов при полном отсутствии интернет-соединения.
* **Жесткая многоарендность (Strict Multi-tenancy):** Обслуживание множества независимых организаций (тенантов) внутри единого экземпляра приложения. Данные, пользователи и контент изолированы на фундаментальном уровне.
* **Стандартизированная интероперабельность:** Полная поддержка стандартов SCORM, xAPI, cmi5, LTI 1.3, EDU-API/SIF из коробки для бесшовного встраивания в любые ИТ-экосистемы.

## 2. Архитектурная модель и Технологический стек

### Фронтенд-архитектура (Изоморфный Rust)

* **Фреймворк:** Rust Leptos (SSR + hydration для публичных страниц, islands-архитектура и `#[server]` RPC-функции для личного кабинета и обучения).
* **Стилизация:** Tailwind CSS для обеспечения легковесного, адаптивного интерфейса на базе единой дизайн-системы.
* **Среда выполнения:** Компиляция клиентской части в WebAssembly (WASM) для обеспечения околонативной производительности интерфейса, сложных интерактивных модулей и сквозного переиспользования типов данных с бэкенда.
* **Доступность (Accessibility):** Целевой уровень — **WCAG 2.2 AA** (см. [`STANDARDS.md`](STANDARDS.md) §«Доступность»). Требования включают:
  * строгое семантическое кодирование компонентов Leptos для корректной работы программ экранного доступа (скринридеров, включая ARIA-атрибуты);
  * сквозную навигацию по всем интерфейсам с клавиатуры (логичный таб-индекс, видимый фокус);
  * **автоматическую валидацию контрастности** пар «текст/фон» и «элемент UI/фон» (SC 1.4.3, SC 1.4.11) при сохранении `branding_config` тенанта. При провале валидации тенант получает предупреждение в UI и предложение ближайшей безопасной пары; сохранение палитры, нарушающей WCAG 2.2 AA, блокируется на уровне API.
  * проверки — axe-core в CI + ручной аудит ключевых сценариев.

### Бэкенд-архитектура

* **Ядро:** Rust (высокопроизводительный асинхронный веб-фреймворк Axum).
* **База данных ядра:** PostgreSQL. Миграции — на базе `sqlx` (основной инструмент) с возможностью использования `SeaORM` для сложных сценариев (см. [`MIGRATIONS.md`](MIGRATIONS.md)). Хранение транзакционных данных, сущностей пользователей, курсов, профилей маппинга и конфигураций тенантов.
* **База данных аналитики (LRS):** Архитектура хранения xAPI-логов высокой интенсивности записи вариативна и определяется на этапе развертывания из двух опций:
  * **Вариант А:** Расширение TimescaleDB для PostgreSQL (сохраняет единый стек СУБД, упрощает администрирование, поддерживает реляционные связи).
  * **Вариант Б:** Выделенный кластер ClickHouse (максимальная производительность сжатия и скорость выполнения аналитических выборок при экстремальных Enterprise-нагрузках).
* **Единый контракт данных:** Общий крейт `shared` с типами данных xAPI и DTO-моделями, используемый одновременно на сервере и клиенте (WASM).

## 3. Функциональная архитектура Мультитенантности (Strict Multi-tenancy)

Платформа поддерживает архитектуру логического разделения данных в рамках одной кодовой базы:

* **Абсолютная изоляция контента:** У каждого тенанта контент всегда строго свой, уникальный. Архитектура базы данных исключает сквозной шеринг или пересечение учебных материалов, пользователей, логов и настроек между организациями. Привязка к `tenant_id` является обязательным сквозным ключом для всех бизнес-сущностей.
* **Маршрутизация через SSO (Идентификация тенанта):** Привязка пользователя к конкретному тенанту и его автоматическая переадресация происходят в момент сквозной авторизации (Single Sign-On — OIDC/SAML2/LDAP). Платформа считывает метаданные Identity Provider (IdP) организации, сопоставляет пользователя с его цифровым контуром и прозрачно авторизует в нужном тенанте. В архитектуру ядра закладывается техническая возможность альтернативной/резервной маршрутизации по поддоменам (например, `client1.lms.domain`).
* **Динамический Provisioning (Создание тенантов через API):** Платформа поддерживает автоматизированное создание новых тенантов посредством вызовов со стороны внешних CRM/биллинг систем через супер-администраторский слой API (см. [`OPEN_API.md`](OPEN_API.md) §3.1). При вызове автоматически генерируется новая изолированная область данных, схема авторизации и корневая учетная запись администратора организации.
* **Кастомизация (White Labeling):** Каждый тенант может настраивать собственную цветовую схему (через динамические переменные Tailwind) и загружать логотипы. Палитра проходит автоматическую валидацию на соответствие WCAG 2.2 AA (см. §2 «Доступность»).

## 4. Иерархия образовательного контента и сущностей

Конструктор курсов предоставляет гибкую многоуровневую структуру для организации обучения внутри каждого тенанта:

* **Программы обучения (Programs):** Высокоуровневая сущность, объединяющая несколько курсов в единый образовательный трек. Поддерживает настройку общих дедлайнов для всей программы, выдачу итоговых дипломов и сквозную аналитику.
* **Курсы (Courses):** Самостоятельная учебная единица внутри тенанта с собственными авторами, преподавателями и зачисленными студентами.
* **Группы обучения (Batches):** Организационные потоки студентов, проходящих одни и те же курсы параллельно в рамках фиксированного расписания. Сущность позволяет централизованно управлять синхронным прогрессом, общими дедлайнами тестов, расписанием вебинаров/живых сессий и групповыми каналами коммуникации для когортного обучения (см. §7.1).
* **Модули / Разделы (Units):** Логический раздел внутри курса, группирующий учебные элементы по темам. Поддерживает правила последовательного прохождения (блокировка юнита до выполнения условий предыдущего).
* **Тесты (Quizzes):** Встроенный движок тестирования с автоматической проверкой знаний. Поддерживает рандомизацию из пула вопросов, различные типы ответов (выбор, соответствие, открытый ввод) и гибкие ограничения (попытки, тайм-лимиты, штрафы).
* **Практические задания (Assignments):** Блок для комплексной проверки практических навыков, требующий ручной оценки ментором. Включает интерфейс рецензирования файлов/эссе в UI Leptos, выставление оценок по критериям и ведение диалога по заданию.
* **Роли пользователей:** `admin`, `instructor`, `mentor`, `learner`, `observer` (см. [`RBAC.md`](RBAC.md) и [`DB_SCHEMA.md`](DB_SCHEMA.md) §«Таблица users»).

### Сертификация и верификация (Certification)

Платформа содержит модуль автоматического и ручного выпуска цифровых сертификатов для превращения успешного обучения в подтвержденные достижения.

* **Триггеры выпуска:** Сертификаты могут выдаваться на основании успешного закрытия отдельного курса, завершения программы обучения (Program), успешного прохождения конкретного организационного потока (Batch) или по факту финальной экспертной оценки.
* **Дистрибуция:** Студенты получают верифицированные цифровые документы, доступные для публичного шеринга в социальных сетях, встраивания в резюме и проверки подлинности внешней стороной по уникальному ID или QR-коду на базе открытых эндпоинтов платформы.

## 5. Архитектура Offline-First PWA и Управление кэшированием

Платформа функционирует как Progressive Web App (PWA) с использованием Service Workers, обеспечивая непрерывность обучения без сети.

### Механика работы без сети и синхронизация

1. **Локальное хранилище (IndexedDB):** Фронтенд на Rust Leptos кэширует структуру программ, курсов, юнитов, текстовые материалы, локальные тесты и WASM-модули верифицированных плагинов.
2. **Управление тяжелым медиа-контентом (Видео/Аудио):** Кэширование тяжелых медиафайлов не является принудительным и гибко управляется настройками:
   * **На уровне платформы:** Администратор тенанта может ограничить офлайн-скачивание видео из соображений защиты авторских прав.
   * **На уровне пользователя:** Студент сам решает, скачивать ли медиаматериалы юнита для изучения в офлайне (с выбором качества), или обучаться без сети только с использованием текста, тестов и легковесных WASM-модулей.
3. **Накопление цифрового следа:** В офлайне все генерируемые xAPI statements и промежуточные состояния (state) плагинов записываются в локальную очередь IndexedDB.
4. **Разрешение конфликтов (Сохранение всех попыток):** При восстановлении сети менеджер синхронизации транзакционно передает данные на бэкенд по принципу At-least-once. Если студент выполнял задания на разных офлайн-устройствах, система гарантированно сохраняет обе попытки в историю LRS, фиксируя точные временные метки их реального прохождения. Хронология цифрового следа не перезаписывается, а финальная оценка рассчитывается на основе политик курса (см. [`OFFLINE_SYNC.md`](OFFLINE_SYNC.md) §5).

## 6. Архитектура плагинов: Гибридный Рантайм (WASM + iframe)

* **Уровень А: Неверифицированные плагины (Изоляция iframe):** Рендеринг сторонних модулей на изолированном поддоменном контуре через `<iframe>` с жестким атрибутом `sandbox="allow-scripts"`. Обмен данными с Event Bus ядра идет исключительно через асинхронный мост `window.postMessage`. Офлайн-режим для таких плагинов ограничен браузерными механизмами.
* **Уровень Б: Верифицированные плагины (Динамический WASM):** Модули компилируются в целевую архитектуру `wasm32-unknown-unknown` и загружаются динамически в единое адресное пространство памяти Leptos-фронтенда. Отличаются максимальной производительностью, реактивным рендерингом через `wasm-bindgen` и полноценной поддержкой Offline-First логики за счет прямого доступа к локальному кэшу ядра.

## 7. Модули: ETL, коммуникации, ВКС

### 7.1. Модуль коммуникаций

Встроенный слой коммуникаций обеспечивает взаимодействие участников обучения без выхода из платформы. Полная спецификация — в [`COMMUNICATIONS.md`](COMMUNICATIONS.md).

* **Чаты:**
  * Личные (1-to-1).
  * Групповые (произвольные).
  * Чаты курса (общий канал когорты).
  * Чаты домашнего задания (привязаны к конкретному assignment).
  * Возможности: Markdown, вложения (файлы), голосовые сообщения, упоминания, реакции.
* **Комментарии к контенту:** Ветка обсуждений под каждым элементом контента (урок, задание, файл, тест) — по аналогии с Google Docs / GitHub. Поддержка резолва треда, упоминаний и уведомлений.
* **Уведомления:** Каналы — In-app, Email, Telegram, Webhook (для внешних систем тенанта), Push (PWA). Правила маршрутизации настраиваются на уровне тенанта и пользователя.

### 7.2. Видеоконференцсвязь (ВКС)

Встроенный модуль ВКС используется для синхронных занятий и живых сессий внутри потоков (Batches). Полная спецификация — в [`CONFERENCING.md`](CONFERENCING.md).

* **Гибридный движок WebRTC:**
  * **P2P (Mesh):** для занятий 1-to-1 — минимальная задержка, без промежуточного сервера.
  * **SFU (Selective Forwarding Unit):** для групп — кандидаты Mediasoup / Janus. Сервер маршрутизирует потоки, экономя ресурсы клиентов.
* **Инструменты:** интерактивная доска (Whiteboard), шеринг экрана, совместный просмотр видео, поднятие руки, опросы в реальном времени.
* **Закрытый контур:** для Air-gapped On-Premise разворачиваются локальные **TURN/STUN** серверы, работающие внутри LAN. Внешние STUN/TURN не используются.

### 7.3. Модуль импорта/экспорта пользователей (Custom ETL Mapper)

Визуальный декларативный конструктор схем данных (Data Mapping Engine) для сопоставления внешних файлов (CSV, XLSX, JSON, XML) с внутренней структурой конкретного тенанта:

* Интерактивная привязка колонок файла к полям профиля, группам или ролям внутри организации.
* Конвейер трансформации (Data Mutation Pipeline) для очистки и нормализации данных на лету (регулярные выражения, маски).
* Сохранение пресетов маппинга для автоматизации регулярных синхронизаций через Open API.

## 8. Слой Открытого API и Менеджмент Токенов (Open API & API Keys)

Для обеспечения бесшовной программной интеграции платформа предоставляет два уровня взаимодействия и разграничения доступа через специализированный Интерфейс выдачи API-токенов.

### Архитектура управления токенами

* **Супер-административный уровень (Глобальные токены):** Выдаются в главной панели управления платформы. Обладают правами на вызов эндпоинтов динамического создания тенантов (`POST /api/v1/internal/tenants`), изменение глобальных лимитов и сбор мета-аналитики. Тип — асимметричные JWT (EdDSA / RS256).
* **Уровень Тенанта (Локальные токены):** Администраторы конкретной организации могут самостоятельно генерировать API-ключи внутри своего личного кабинета. Эти токены жестко привязаны к конкретному `tenant_id` и имеют гранулярные области видимости (Scopes: `users:sync`, `grades:read`, `courses:write`). Тип — Opaque Tokens (непрозрачные строки с префиксом).
* **Безопасность:** Глобальные и локальные токены — строго разные типы (см. [`OPEN_API.md`](OPEN_API.md) §2). Система отображает секретный ключ один раз при создании, храня в БД только его хэш (SHA-256). Внедряется механизм ротации и отзыва ключей в реальном времени.

### Ключевые группы эндпоинтов Open API

1. **Управление инфраструктурой (Глобальный API):** Динамическое создание, блокировка и конфигурирование тенантов.
2. **Управление пользователями (`/api/v1/users`):** Программный запуск кастомного импорта внутри тенанта, создание, синхронизация оргструктуры и распределение учащихся по потокам (batches).
3. **Управление обучением (`/api/v1/courses`, `assignments`, `quizzes`):** Программное назначение программ, курсов и модулей сотрудникам.
4. **Аналитический экспорт (`/api/v1/analytics`):** Прямой стриминг raw-данных xAPI (JSON-LD), итоговых ведомостей успеваемости и реестра выданных сертификатов (certificates) во внешние BI-платформы.
5. **Событийные Вебхуки (Webhooks Engine):** Асинхронное уведомление внешних систем (CRM, ERP, HRM) о ключевых триггерах с гарантированной доставкой.

## 9. Обработка тяжелых фоновых задач (Подход к реализации)

Для выполнения ресурсоемких операций (массовый импорт пользователей тенанта, расчет аналитики программ, рассылки) бэкенд защищается от блокировки потоков API. Выбор архитектуры очереди вариативен и будет сделан на более поздних этапах из двух вариантов:

* **Подход 1 (Внутренний):** Легковесные In-Memory Tokio Tasks внутри серверного процесса. Простота коробки, высокая скорость. Для минимизации рисков потери задач при перезапуске бэкенда внедряется механизм Graceful Shutdown (до 30 секунд на завершение активных задач); полной отказоустойчивости не даёт.
* **Подход 2 (Внешний):** Распределенная очередь задач на базе River (PostgreSQL), Redis или аналогов. Абсолютная отказоустойчивость, персистентность задач, возможность выделения отдельных серверов-воркеров под тяжелые импорты.

## 10. Поэтапный план работ (Roadmap)

### Этап 1: Архитектурный фундамент, IAM, Жесткая Мультитенантность и Open API Core

* Проектирование схемы БД (PostgreSQL) с жестким разделением данных (`tenant_id`) и структуры аналитического хранилища (LRS).
* Реализация интеграции SSO для авторизации и автоматического определения тенантов, разработка интерфейсов генерации локальных и глобальных API-токенов.
* Разработка базовой дизайн-системы на Tailwind CSS и каркаса приложения на Rust Leptos с заложенной доступностью по WCAG 2.2 AA (скринридеры, клавиатурный фокус, валидация контраста палитры).

### Этап 2: Конвейер импорта (ETL), Иерархия контента и Хранилище аналитики (LRS)

* Разработка конструктора кастомного импорта пользователей (ETL-парсер файлов с маппингом полей), внешняя интеграция с механизмами фоновых задач.
* Реализация структуры сущностей: Программы (Programs), Курсы (Courses), Группы совместного обучения (Batches) и Модули (Units) с жесткой привязкой к тенанту.
* Запуск слоя LRS (варианты на базе TimescaleDB или ClickHouse) для фиксации учебных действий.

### Этап 3: Движок аттестации, Модуль коммуникаций, Сертификация и Базовый PWA-каркас

* Разработка конструктора и рантайма Тестов (Quizzes) и Практических заданий (Assignments).
* Разработка модуля коммуникаций: чаты (личные / групповые / курс / задание), комментарии к контенту, уведомления (in-app, Email, Telegram, Webhook, Push).
* Проектирование сервиса генерации, автоматического рендеринга и публичной верификации цифровых сертификатов (Certification Module).
* Интеграция конфигурации PWA и Service Workers в Leptos-приложение, обеспечение базового офлайн-доступа к структуре контента.
* Разработка Plugin SDK с поддержкой postMessage моста для iframe.

### Этап 4: Высокопроизводительный Офлайн-режим (Offline-First), Динамический WASM и ВКС

* Оптимизация Leptos для динамической потоковой подгрузки доверенных WASM-модулей плагинов в рантайме.
* Реализация клиентского менеджера синхронизации (Sync Manager) с логикой сохранения всех конфликтующих попыток в LRS и локального хранилища IndexedDB.
* Внедрение панели настроек кэширования медиаконтента (видео/аудио) для управления загрузкой на устройство пользователя.
* Разработка модуля ВКС: гибридный движок WebRTC (P2P для 1-to-1, SFU для групп), инструменты (whiteboard, шеринг, опросы), локальные TURN/STUN для Air-gapped.

### Этап 5: Стандартизация, Оптимизация и Упаковка (Коробка)

* Внедрение поддержки внешних стандартов: SCORM/cmi5 и LTI 1.3 (Consumer/Provider).
* Финальное стресс-тестирование синхронизации вебхуков Open API, проверка соответствия WCAG 2.2 AA (скринридеры, клавиатура, контрастность).
* Упаковка всей мультитенантной инфраструктуры платформы в изолированные контейнеры (Docker-compose / Helm-charts) для On-Premise поставки в Air-gapped контуры.
