# Спецификация Технического Задания: Руководство для разработчиков внешних плагинов

**Файл спецификации:** `specs/PLUGIN_DEVELOPMENT_TEMPLATE.md`

> Обязательное расширение [`PLUGIN.md`](PLUGIN.md). Требования к доступности (a11y) в платформе — в [`STANDARDS.md`](STANDARDS.md) §«Доступность». Требования к процессу верификации и подписи плагинов Контура Б — в [`PLUGIN.md`](PLUGIN.md) §7.

## 1. Введение и назначение шаблона

Настоящий документ является обязательным расширением [`PLUGIN.md`](PLUGIN.md) и служит унифицированным техническим заданием для команд, разрабатывающих внешние интерактивные модули (микроприложения) для интеграции в LMS-платформу.

Любой внешний плагин должен строго соответствовать описанным ниже интеграционным сценариям, протоколам обмена данными, требованиям к визуальной адаптивности и требованиям к доступности (a11y), чтобы гарантировать корректную работу в изолированных iframe-песочницах и Offline-First PWA-контуре Ядра.

**Область действия a11y.** Платформа обеспечивает доступный контейнер (iframe + обвязка Ядра), но **содержимое плагина** — ответственность разработчика. Требования WCAG 2.2 AA, заявленные платформой, распространяются на содержимое **собственных** плагинов платформы и на **референсные** Enterprise-модули. Для сторонних плагинов требования a11y ниже — обязательны к выполнению для перехода в Контур Б (верифицированные).

## 2. Сценарии интеграционного взаимодействия (Use Cases)

Разработчик внешнего плагина обязан спроектировать внутреннюю архитектуру микроприложения таким образом, чтобы она бесшовно поддерживала четыре фундаментальных сценария жизненного цикла платформы.

### Сценарий 1: Инициализация и адаптация (OnMount & Hydration)

* **Предусловие:** Пользователь переходит на Юнит курса, содержащий плагин. Ядро монтирует контейнер плагина в DOM.
* **Алгоритм взаимодействия:**
  1. Плагин инициализирует внутренние слушатели событий и переходит в режим ожидания.
  2. Ядро императивно вызывает метод SDK `init()`, передавая структуру `PluginContext`.
  3. Плагин принимает контекст, извлекает параметры кастомизации (`branding_config`) и динамически перестраивает свой интерфейс (подменяет css-переменные Tailwind для соответствия цветам тенанта). **При этом палитра тенанта уже прошла валидацию контраста на стороне Ядра (см. [`STANDARDS.md`](STANDARDS.md) §«Доступность»)** — разработчику не нужно самостоятельно проверять контраст гексакодов тенанта, но нужно убедиться, что цвета не «смешиваются» некорректно.
  4. Плагин вызывает метод SDK `loadState()` для проверки наличия сохраненного прогресса данного пользователя.
  5. Если Ядро возвращает пустую строку, плагин запускает интерактив с начального экрана (нулевая точка). Если Ядро возвращает JSON-строку состояния, плагин парсит её, восстанавливает сессию (например, выставляет элементы интерфейса на те же позиции, где пользователь закончил работу) и переходит в статус `RUNNING`.

### Сценарий 2: Фиксация промежуточного прогресса (State Persistence)

* **Предусловие:** Пользователь совершает действия, меняющие внутреннее состояние интерактива, или закрывает плагин.
* **Алгоритм взаимодействия:**
  1. С шагом в определенное количество действий (или по внутренним контрольным точкам) плагин формирует снимок своей памяти в виде плоской JSON-строки.
  2. Плагин вызывает метод SDK `saveState(state_json)`.
  3. **В режиме онлайна:** Ядро транслирует эту строку через API на бэкенд для записи в PostgreSQL.
  4. **В режиме офлайна:** Ядро перехватывает вызов и атомарно записывает строку в локальную базу IndexedDB устройства под композитным ключом сессии.
  5. Плагин получает подтверждение от SDK и продолжает работу, не заботясь о физическом сетевом статусе устройства.

### Сценарий 3: Стриминг учебного следа (xAPI Event Streaming)

* **Предусловие:** Пользователь совершает значимое образовательное действие (ответил на микро-вопрос, завершил симуляцию, совершил ошибку).
* **Алгоритм взаимодействия:**
  1. Плагин генерирует внутреннее сырое событие, упаковывая его в структуру `RawPluginEvent` (строковый маркер действия + контекстные параметры в JSON).
  2. Плагин вызывает метод SDK `sendEvent(event)`.
  3. Сообщение мгновенно передается в шину событий Ядра.
  4. Плагин не ожидает завершения обработки события бэкендом и сразу возвращает управление пользователю (асинхронный неблокирующий вызов). Маппинг события в xAPI Statement и его валидация происходят на стороне Ядра.

### Сценарий 4: Экстренное завершение работы (Graceful Shutdown)

* **Предусловие:** Пользователь кликает на кнопку «Следующий юнит» в интерфейсе Ядра или закрывает вкладку PWA.
* **Алгоритм взаимодействия:**
  1. Ядро переводит конечный автомат плагина в состояние `TERMINATING` и отправляет плагину принудительный сигнал закрытия.
  2. Плагин обязан мгновенно заблокировать UI (отобразить лоадер), прервать активные таймеры, собрать финальный снимок прогресса и вызвать метод SDK `saveState()`.
  3. На выполнение всей цепочки сохранения плагину выделяется 800 миллисекунд. По истечении этого лимита Ядро аппаратно уничтожает контейнер плагина из DOM, освобождая память. Плагин должен быть спроектирован так, чтобы процедура консервации данных гарантированно укладывалась в этот тайм-аут.

## 3. Спецификация форматов обмена сообщениями (postMessage Data Contracts)

Для плагинов, работающих в контуре Неверифицированных (через iframe), обмен данными регламентируется строгими JSON-контрактами через `window.postMessage`. Разработчик плагина обязан генерировать сообщения, в точности соответствующие следующим схемам.

### 3.1. Структура исходящего сообщения от Плагина к Ядру (Запрос действия)

Каждое сообщение, посылаемое плагином вверх в родительское окно Ядра, должно представлять собой JSON-объект со следующей структурой полей:

* `sdk_method`: Строка. Строго одно из значений: `'saveState'`, `'loadState'`, `'sendEvent'`.
* `session_token`: Строка. Криптографический токен, полученный плагином от Ядра в момент инициализации `init()`. Служит для валидации права записи.
* `payload`: JSON-объект. Внутреннее наполнение, зависящее от вызываемого метода:
  * Для `saveState`: Строка `state_data`, содержащая внутренний дамп плагина.
  * Для `sendEvent`: Объект с полями `event_name` (строковый маркер) и `event_properties` (произвольный JSON-объект с метриками действия).

### 3.2. Структура входящего сообщения от Ядра к Плагину (Ответ / Триггер)

Плагин должен настроить слушатель сообщений от родительского окна и обрабатывать входящие JSON-объекты следующего вида:

* `status`: Строка. Принимает значения `'success'` или `'error'`.
* `correlation_id`: Строка. Уникальный UUID запроса, позволяющий плагину понять, на какой именно асинхронный вызов (`saveState` или `loadState`) пришел данный ответ.
* `data`: JSON-объект или Строка. Полезный ответ ядра. Для `loadState` здесь будет содержаться ранее сохраненная JSON-строка прогресса.
* `error_context`: JSON-объект (NULLable). Заполняется деталями ошибки (например, `'INVALID_SESSION_TOKEN'`, `'STORAGE_LIMIT_EXCEEDED'`), если статус равен `error`. При получении ошибки плагин обязан корректно обработать её в интерфейсе, не допуская аварийного завершения рантайма.

## 4. Требования к UI/UX и дизайн-системе плагина

Внешнее микроприложение должно выглядеть как нативная, органичная часть платформы, независимо от того, какой тенант (организация) его запустил.

### 4.1. Динамическая тема (Theming)

* Плагину запрещено жестко зашивать в свой код (hardcode) фоновые цвета, цвета кнопок, шрифты и стили элементов управления.
* При вызове `init()` плагин получает карту цветов тенанта. Разработчик обязан применить эти гексакоды к CSS-переменным своего приложения.
* При изменении темы в Ядре плагин должен динамически перерисовывать UI.

### 4.2. Адаптивность и сетка (Layout Constraints)

* Контейнер плагина может рендериться на мобильных экранах, планшетах или внутри узкой контентной колонки десктопного интерфейса.
* Плагин должен быть спроектирован по принципу Mobile-First с использованием гибкой (Fluid) верстки Tailwind или CSS Flexbox/Grid.
* Плагин обязан занимать ровно 100% ширины и высоты выделенного ему родительского iframe-контейнера, корректно обрабатывая события изменения размера окна (`resize`).

### 4.3. Запрет на собственную навигацию

* Плагину категорически запрещено отрисовывать собственные глобальные элементы навигации, дублирующие функции Ядра (кнопки «Назад», «Вперед», «Выход из курса», шапки профиля или боковые меню).
* Плагин управляет исключительно внутренним интерактивным холстом учебного элемента.

### 4.4. Доступность (a11y)

Плагин обязан соответствовать **WCAG 2.2 AA** в части, которую он контролирует. Платформа обеспечивает доступный контейнер, но содержимое — на стороне разработчика (см. [`STANDARDS.md`](STANDARDS.md) §«Доступность»).

Обязательные требования:

* **Семантика и ARIA.** Использовать семантические HTML-элементы (`<button>`, `<nav>`, `<main>`, `<form>`, `<label>`) вместо `<div>`-обёрток. Для нестандартных интерактивных элементов — ARIA-атрибуты (`role`, `aria-label`, `aria-describedby`). Интерактивные элементы обязаны иметь доступное имя (accessible name).
* **Клавиатурная навигация.** Все интерактивные элементы должны быть достижимы с клавиатуры (`Tab`), активироваться `Enter`/`Space`, иметь видимый фокус (не отключать `outline` без визуальной замены). Ловушки фокуса (focus traps) запрещены; если плагин открывает модальное окно, фокус должен корректно возвращаться после закрытия.
* **Контрастность.** Текст и элементы UI должны соответствовать SC 1.4.3 (минимум 4.5:1 для обычного текста, 3:1 для крупного) и SC 1.4.11 (3:1 для элементов UI и графики). Палитра тенанта уже прошла валидацию на стороне Ядра, но разработчик обязан проверить, что его собственные дополнительные цвета (например, статусы «правильно/неправильно» в симуляции) также соответствуют WCAG.
* **Локализация и RTL.** Корневой элемент плагина обязан выставлять атрибут `lang` в соответствии с локалью пользователя (передаётся в `PluginContext`). Для RTL-языков (арабский, иврит) — поддержка `dir="rtl"`, зеркальные отступы, адаптация иконографики.
* **Медиа.** Автовоспроизведение видео/аудио запрещено без явного действия пользователя. Медиа-элементы должны иметь элементы управления (`controls`) и, при наличии, субтитры/транскрипт.
* **Движущийся контент.** Анимации продолжительностью > 5 секунд должны иметь возможность остановки (SC 2.2.2). Для пользователей с `prefers-reduced-motion` — отключать или сокращать анимации.
* **Формы.** Все поля обязаны иметь `<label>`, ассоциированный с полем. Ошибки валидации — озвучиваться скринридером (`aria-live`) и визуально подсвечиваться не только цветом.

## 5. Чек-лист готовности плагина к передаче на верификацию (Definition of Done)

Перед тем как плагин будет переведён из Контура А (изолированный iframe) в Контур Б (нативный динамический WebAssembly с прямым доступом к памяти фронтенда), команда разработки плагина обязана подтвердить соответствие следующим критериям:

1. **Изоляция данных:** Плагин не совершает попыток прямого чтения `window.parent.document`, кук родительского домена или глобальных хранилищ браузера. Все взаимодействие идёт строго через Plugin SDK.
2. **Безопасность сетевых запросов:** Плагин не содержит зашитых внешних URL-адресов. В режиме iframe плагин полностью работоспособен при включённых заголовках CSP `connect-src 'none'`.
3. **Регламент Graceful Shutdown:** Финальное сохранение состояния при получении сигнала `TERMINATING` гарантированно укладывается в 800 миллисекунд на аппаратных мощностях средней конфигурации.
4. **Типобезопасность контрактов:** Все генерируемые сырые события (`RawPluginEvent`) задокументированы, имеют фиксированные строковые маркеры и передаются бэкенду Ядра вместе с готовой таблицей маппинга в xAPI-глаголы.
5. **Стабильность памяти:** В плагине отсутствуют утечки памяти (Memory Leaks) при многократных циклах монтирования/демонтирования (Mount/Unmount) компонента в рамках одной сессии пользователя.
6. **Доступность (a11y):** Плагин проходит автоматическую проверку `axe-core` без критических и серьёзных (critical / serious) нарушений. Плагин проходит ручную проверку клавиатурной навигации: все интерактивные элементы достижимы и активируемы с клавиатуры, фокус виден, ловушек фокуса нет. Для RTL-локалей — проверен внешний вид и навигация.
7. **Подпись и верификация (для Контура Б):** Артефакт `.wasm` подписан release-ключом платформы, файл `.wasm.sig` приложен. Плагин не находится в Revocation List на момент верификации. Процесс — см. [`PLUGIN.md`](PLUGIN.md) §7.
