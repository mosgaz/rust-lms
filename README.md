# Модульная мультиарендная LMS-платформа (Full-Stack Rust Core)

**Файл спецификации:** `README.md`

Высокопроизводительная образовательная платформа корпоративного уровня (Enterprise-grade), спроектирована на базе изоморфного стека **Full-Stack Rust** с жёсткой изоляцией данных организаций (**Strict Multi-tenancy**), двухуровневым рантаймом плагинов (**WebAssembly / iframe**) и архитектурой **Offline-First PWA**.

> **Примечание об изоморфности.** Стек является изоморфным в части ядра приложения (SSR + WASM-гидратация на Leptos). Единственное исключение — исполнение **неверифицированных сторонних плагинов**, которое намеренно вынесено в браузерную песочницу `iframe`. Это архитектурное решение принято ради безопасной изоляции недоверенного кода и не нарушает изоморфности основного приложения.

> **Текущий этап проекта.** Активная реализация серверного ядра (`rust-lms-api` + `rust-lms-server`). Внедрена Identity-First архитектура (ADR 2026.10.05-0011): глобальная личность (`identities`) + роли в тенантах (`users`), двухшаговая аутентификация с авто-выбором `preferred_tenant_id`. Матрица готовности фич ведётся в [`specs/STATUS.md`](specs/STATUS.md).

## 🛠️ Технологический стек проекта

- **Backend Хост (Сетевой рантайм):** Rust 1.80+ (асинхронный веб-фреймворк `Axum`, крейт `rust-lms-server`). Чистая бизнес-логика на базе плоских сервисов и контрактов — крейт `rust-lms-api`.
- **Application UI & RPC Слой:** Rust `Leptos 0.8+` (SSR-рендеринг + клиентская WASM-гидратация, RPC-взаимодействие через `#[server]`-функции).
- **Стилизация интерфейса:** `Tailwind CSS` (динамические дизайн-системы тенантов).
- **Основная база данных (Core):** `PostgreSQL 15+` с принудительной изоляцией строк на уровне СУБД через политики `Row-Level Security (RLS)`. Гарантия RLS действует для реляционного слоя; для аналитического слоя LRS (Вариант Б) изоляция обеспечивается архитектурно — см. [`specs/DB_SCHEMA.md`](specs/DB_SCHEMA.md) §2 Вариант Б.
- **Миграции БД:** `sqlx` (compile-time проверяемые миграции) — единственный инструмент для миграций и операций записи (INSERT / UPDATE / DELETE). `SeaORM` допускается **только** для генерации типов из существующей схемы и построения сложных SELECT-запросов; использование `SeaORM` для миграций и записи запрещено (см. [`specs/CODING_STANDARDS.md`](specs/CODING_STANDARDS.md) §2.3).
- **Аналитическое хранилище (LRS):** Инвариантный слой с поддержкой `TimescaleDB` (гипертаблицы) как рекомендованного решения для развёртываний с ограниченным TCO. Сбор, агрегация xAPI-логов и телеметрии встроенного прокторинга. Использование внешних OLAP-кластеров вроде `ClickHouse` исключено для снижения стоимости владения инфраструктурой; при необходимости масштабирования допускается архитектурный вариант Б (см. [`specs/DB_SCHEMA.md`](specs/DB_SCHEMA.md) §2 Вариант Б).
- **Локальное хранилище PWA:** `IndexedDB` (через экосистему `web-sys / gloo`) для удержания транзакционных офлайн-очередей.
- **ВКС (видеоконференцсвязь):** Гибридный WebRTC-движок (P2P Mesh для 1-to-1, SFU Mediasoup/Janus для групп), локальные TURN/STUN для закрытых контуров.
- **Архитектура плагинов:** Изолированные контейнеры на базе WebAssembly (рантайм `Wasmtime` на сервере) и `iframe`-песочницы на стороне клиента для безопасного выполнения стороннего EdTech-контента и кастомных модулей аттестации.

## 📦 Архитектура Cargo Workspace (Структура крейтов)

Проект разработан в виде монорепозитория, разделённого на **семь** специализированных микро-крейтов. Имя крейта в `Cargo.toml` имеет префикс `rust-lms-`, путь в файловой структуре — без префикса. Полная карта и правила изоляции — в [`specs/STRUCTURE.md`](specs/STRUCTURE.md).

| Путь | Имя крейта | Назначение |
|:---|:---|:---|
| `crates/shared/` | `rust-lms-shared` | Плоские DTO, сущности (Identity, User, Tenant, Courses, Batches), контракты обмена и xAPI JSON-LD структуры. **Framework-agnostic: ноль зависимостей от веб-фреймворков, СУБД и UI (только `serde`/`serde_json` для сериализации контрактов).** |
| `crates/ui/` | `rust-lms-ui` | Чистая библиотека переиспользуемых атомарных компонентов и блоков вёрстки дизайн-системы (Tailwind CSS, доступность по WCAG 2.2 AA, Fluent-локализация). |
| `crates/icons/` | `rust-lms-icons` | Типизированная библиотека SVG-иконок дизайн-системы с поддержкой Leptos. |
| `crates/api/` | `rust-lms-api` | Серверное ядро бизнес-логики, слой взаимодействия с базами данных (PostgreSQL + RLS менеджер) и LRS-аналитика. **Без зависимостей от макросов Leptos.** |
| `crates/client/` | `rust-lms-client` | Изоморфное full-stack веб-приложение на Leptos. Отвечает за маршрутизацию, авторизацию и UI. Включает публичный сайт (`website`), студенческий кабинет (`student`) и лениво загружаемую панель управления (`cpanel`). |
| `crates/server/` | `rust-lms-server` | Точка входа бэкенда хоста на Axum, инициализация СУБД пулов, раздача WASM-статики и запуск планировщиков Tokio. |
| `crates/cli/` | `rust-lms-cli` | Автономная CLI-утилита (`rust-lms`) для администрирования в Air-gapped (управление лицензиями, feature flags, conformance-тесты). |

**Правило именования:** в тексте документации путь пишется как `crates/api/`, имя крейта — как `rust-lms-api`. Смешивать нельзя. Устаревшие схемы (`lms-core-*`, `lms-database-*`, `lms-task-*`, `lms-etl-*`, `lms-lrs-*`) запрещены.

## 🔒 Безопасность и нормативное соответствие (ФСТЭК & 152-ФЗ)

Проект изначально разрабатывается в соответствии с методологией безопасной разработки программного обеспечения (**ГОСТ Р 56939**). Архитектурные решения учитывают требования ФСТЭК России к государственным информационным системам (ГИС) до **К1** включительно и информационным системам персональных данных (ИСПДн) до **УЗ-1** включительно.

- Изоляция данных на уровне СУБД (PostgreSQL RLS) полностью исключает межконтурные утечки и серые зоны интеграции.
- Полное отсутствие `unsafe` кода в бизнес-логике гарантирует защиту от уязвимостей управления памятью. Дополнительно см. [`specs/CODING_STANDARDS.md`](specs/CODING_STANDARDS.md) §1.1 — запрет `unsafe` в крейтах `api`, `server`, `client`, `ui`; исключение только для низкоуровневых WASM-мостов с обязательным комментарием `// SAFETY:` и ревью Архитектурного комитета.
- Проект поддерживает автономное развёртывание в изолированных защищённых контурах (**Air-gapped** инсталляции).
- Все правила безопасной разработки, включая запрет `unwrap()`/`expect()` в runtime, обязательный `// SAFETY:` для низкоуровневых WASM-мостов, контроль supply chain через `cargo-audit`/`cargo-deny` и защиту ПДн при логировании, зафиксированы в [`specs/CODING_STANDARDS.md`](specs/CODING_STANDARDS.md) §§ 1.1, 2.2, 7, 9, 10, 11.

## 🧪 Тестирование

### Unit-тесты (не требуют БД)

Unit-тесты проверяют изолированные компоненты: хеширование паролей (Argon2id), генерацию/валидацию JWT, маппинг ошибок репозиториев и handlers, работу middleware.

```bash
# Запуск всех unit-тестов воркспейса
cargo test --workspace --lib

# Запуск unit-тестов конкретного крейта
cargo test -p rust-lms-api --lib
cargo test -p rust-lms-shared --lib

# Запуск конкретного теста по имени
cargo test -p rust-lms-api --lib test_error_display_invalid_credentials
```

**Покрытие:** ≥80% для модулей `auth/`, `database/repositories/`, `http/`.

### Интеграционные тесты (требуют PostgreSQL)

Интеграционные тесты проверяют полный HTTP-цикл: DTO → БД → REST → Axum-хост, включая Identity-First аутентификацию и RLS-изоляцию.

**Предварительные требования:**

- PostgreSQL 15+ запущен и доступен.
- Переменная окружения `DATABASE_URL` установлена и указывает на пустую или тестовую базу данных.
- Пользователь БД имеет права `CREATE DATABASE` (макрос `#[sqlx::test]` автоматически создаёт временные БД для каждого теста).

```bash
# 1. Установка DATABASE_URL
export DATABASE_URL="postgres://postgres:postgres@localhost:5432/rust_lms_test"

# 2. Запуск интеграционных тестов API
cargo test -p rust-lms-api --test integration_test

# 3. Запуск всех тестов (unit + integration)
cargo test --workspace
```

**Что проверяют интеграционные тесты (`crates/api/tests/integration_test.rs`):**

- ✅ **Авто-выбор тенанта** — если у `identity` установлен `preferred_tenant_id` и он активен, `POST /api/v1/auth/login` сразу возвращает финальные токены (`access_token` + `refresh_token`).
- ✅ **Двухшаговый поток** — если `preferred_tenant_id` отсутствует или невалиден, `login` возвращает `session_token` (TTL 5 мин) и список `available_tenants`; затем `POST /api/v1/auth/select-tenant` выдаёт финальные токены.
- ✅ **Обновление предпочтений** — после `select_tenant` поле `preferred_tenant_id` в таблице `identities` обновляется для бесшовного входа в следующий раз.
- ✅ **Защита от подмены `tenant_id`** — попытка выбрать тенант, к которому у личности нет доступа, отклоняется (401/403).
- ✅ **RLS-изоляция** — пользователь тенанта A не может получить данные пользователя тенанта B, даже имея валидный JWT (ожидаем 404 Not Found).
- ✅ **Неверные учётные данные** — неверный email/пароль возвращает 401 Unauthorized.
- ✅ **Refresh token flow** — `POST /api/v1/auth/refresh` выдаёт новую пару токенов без повторного ввода пароля.
